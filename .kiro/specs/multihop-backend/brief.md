# Brief: multihop-backend

## Problem
利用者は、出口の国に出る前に、1 つ以上の入口の国を経由して接続したい。現在の仕組みは、接続が 1 本のトンネルと 1 つのプロバイダを前提にしているため、経由する段（hop）を表せない。
この spec は、経由する段を n 段まで扱えるバックエンド（ゲートウェイ・API・接続状態）を扱う。画面は別の spec（`multihop-ui`、保留中）で扱う。

## Current State
- ゲートウェイ（`proxy`）とランナー（`runner-protonvpn`・`runner-adguardvpn`）は、すべて `network_mode: host`。経路表と nftables を共有している（`compose/gateway.yml`・`vendors/*/compose.yml`）。
- トンネルは 1 本だけを前提にしている。`vpnIface` は 1 つの文字列で、出口は 1.1.1.1 への経路から 1 つ検出する（`proxy/src/network/connection-monitor.ts`）。
- 接続の API は、プロバイダ 1 つと接続先 1 つを受け取る（`proxy/src/server.ts`・`api/src/routes/providers.ts`）。
- プロファイル（`vendors/*/profile.json`）に、多段接続の宣言はない。
- ProtonVPN の起動処理は、`proton[0-9]+` の名前のインターフェースを起動時に消す。2 本目以降のトンネルと干渉する。
- Secure Core は、アプリの画面やコードでは使っていない（E2E のモックにだけ出てくる）。このため、移行の作業は小さいと見ている（設計で確認する）。

## Desired Outcome
- 出口の前に、n 段（n ≥ 1）の入口を経由して接続できる。段は出口の 1 つ前から順に増やせる作りにする。段が 1 つのときは、今の 2 段（入口 1 + 出口）と同じ結果になる。
- 各段の接続先は、選んだ方式で決める。方式は段ごとに選べる。
- 入口の選び方は 3 方式（既定はランダム）。プロバイダ選択の既定の提供元は、出口と同じプロバイダ。
- どこかの段が切れたときの動作は、設定で選べる。既定は「どの段の切断でも遮断」。
- 段数 n の上限は、設定値として持つ（値は design で決める）。

## Approach
実験で成立が確認された方式を、段の数に依らない形で一般化する（`.kiro/discovery/multihop-chain-input.md` の section 14〜16）。
- **段ごとに Docker のネットワーク（bridge）を分ける。** 段 i のコンテナは、外側（段 i+1、最後は出口）のネットワーク経由で接続する。前段のコンテナは NAT（MASQUERADE）で内側の通信を中継し、内側の既定経路は外側の段へ向ける。
- **段ごとに経路表を分ける。** 段 i の中継と既定経路は、段 i のトンネルの経路表を使う（ProtonVPN の場合の `ip rule`。section 16）。段の数だけ経路表の番号を割り当てる。
- **各デバイスのログイン情報は、作ったときの MAC アドレスに固定して割り当てる。** MAC を変えると、CLI がローカルのログイン情報を破棄することを確認した（section 14）。段ごとにコンテナを作り直しても、MAC が同じならログインは残る。
- 案 A の namespace 方式（`ip netns`）は、AdGuard VPN で登録の失効が起きたため採らない（section 9〜13）。

検証済みの範囲: AdGuard VPN と ProtonVPN の両方で、**同じプロバイダ同士の 2 段**（JP → US）が成立。
**異なるプロバイダの組み合わせ（例: 入口 AdGuard VPN・出口 ProtonVPN）と、3 段以上は、この spec の範囲に含める。** 未検証のため、設計の段階で実機確認を入れる。

### 入口（段）の選び方
- ランダム（既定）: 候補から無作為に選ぶ。
- プロバイダ選択: 既定の提供元は出口と同じ。提供元の方式で選ぶ（AdGuard VPN は ping の最小、ProtonVPN は Score の最小）。
- 手動選択: 利用者が指定した接続先を使う。

段ごとに選んだ結果は、バックエンドが解決して返す（画面は表示するだけ）。

## Scope
- **In**:
  - 段の表現（出口の 1 つ前から順に増やせる、段の配列。段数は n）と、段ごとのネットワーク・MAC・経路表の割り当て
  - 段ごとのトンネルの起動・切断、中継（NAT と既定経路）、ProtonVPN の起動処理の修正（既存のトンネルを消さない）
  - 段ごとの入口の 3 方式の解決（プロバイダごとの方式を含む）
  - 段の失敗時の動作（既定は遮断。段を外して継続を選べる）
  - 接続状態（複数トンネル）と、API の形（段の一覧・段ごとの方式・失敗時の動作を受け取り、接続状態を返す）
  - 既存の 1 段接続（段が 1 つ）の動作を壊さない
  - **異なるプロバイダの組み合わせ**: 段ごとに提供元が違う接続。段ごとのベンダーの起動・切断・経路の扱いを、同じ仕組みで扱う。
  - **n 段**: 段数を増やしても、同じ仕組みで動く作り（段数の上限は設定値）
- **Out**:
  - 画面（タブ・一覧・スイッチ・ラジオ）。`multihop-ui` で扱う。
  - 同時接続の上限の検出や拒否（規約への対応は注意表示のみ。表示は画面の仕事）
  - 段数の動作確認（検証は 2 段で行い、3 段以上は design で決める範囲の実機確認にとどめる）

## Boundary Candidates
- **ネットワーク層**: 段ごとのネットワーク、MAC の割り当て、中継、経路表と経路の向き。ゲートウェイ（`proxy`）とランナーのコンテナ構成。
- **接続の状態と制御**: 段の一覧、段ごとの接続・切断、失敗時の動作、接続状態の集約（`proxy` の状態モデル・`api` の接続 API）。
- **入口の選択**: 段ごとの 3 方式の解決。プロバイダごとの方式（ping・Score）の利用。`location-city-selection` と `location-distance-sort` の一覧データを読むだけで、一覧の取得の仕組みは変えない。

## Out of Boundary
- 画面（表示・操作・タブ・スイッチ）。
- `location-city-selection`・`location-distance-sort` が持つ、都市の一覧の取得・保存・座標の仕組み。
- 規約の判断（注意表示の文言を含む）。

## Upstream / Downstream
- **Upstream**:
  - `location-city-selection`（都市の一覧。入口の候補を作る）
  - `location-distance-sort`（座標・距離。入口の候補の並べ替えに使う場合のみ）
  - `e2e-tests`（多段接続のモックを追加する場合の基盤）
- **Downstream**:
  - `multihop-ui`（保留。画面は既存 spec の対応後に統合して検討する）

## Existing Spec Touchpoints
- **Extends**: なし（今は既存 spec の要件を変えない）。ただし、`location-city-selection`・`location-distance-sort` と同じ接続・一覧のコードを触るため、衝突に注意する。
- **Adjacent**: `location-city-selection`（都市の一覧）、`location-distance-sort`（距離順）、`e2e-tests`（モック）。

## Constraints
- **同時接続の上限（利用者の決定・改訂）**: この spec では同時接続の上限を設けない。超過の扱いは注意表示のみ（EULA の台数制限への注意）。5 本は検証の到達点であり、要件の上限ではない。
- **MTU の調整（利用者の決定）**: 段が増えて MTU が下がる分は、MTU を上げる方向の調整も対象にする。ルータへの設定が必要な場合も対応できる（本番のルータの変更を含む）。
- **検証環境（利用者の決定）**: 最初の検証は検証サーバ（192.168.3.240）で行う。実ベンダへのログインは可能（ProtonVPN の 2FA・AdGuard VPN のデバイス登録は、利用者の操作を伴う）。
- **段数と規約**: 段ごとに、同じアカウントのログインを 1 台分使う。AdGuard VPN の EULA は同時に接続するインスタンス数を制限しうる（無料 2・Unlimited 10）ため、段数が増えるほど上限に近づく。Proton の上限は未確認（無料プランでは二段は成立しない）。利用者の判断により、注意表示のみを行う。
- **MAC の固定**: 各段のコンテナは、ログインを作ったときの MAC を使う。MAC を変えると、ログインが消える。
- **MTU**: トンネルの中にトンネルを張るため、段ごとに MTU が下がる（1 段あたり約 60 バイト減の計算値）。段数 n に応じて決める必要があり、未検証。
- **ライセンス**: AdGuard CLI は商用 EULA のため、イメージを公開レジストリに置く場合は注意（EULA §4.1）。
- **既存の制約**: 公開リポジトリのため秘密情報を CI に渡さない（`e2e-tests` の制約を引き継ぐ）。
- **1 プロバイダ前提の現状**: 接続状態は 1 プロバイダに 1 つ。プロバイダの切替（`ProviderSelector`）は接続を切断してから行う。異なるプロバイダの組み合わせと段の配列では、この前提を段ごとに持ち直す必要がある（状態モデルと API の形の変更を含む）。
- **ベンダーどうしの干渉**: ProtonVPN の起動処理は `proton[0-9]+` のインターフェースを消すため、他の段と同居させるときは、消す範囲を Proton の段に限る必要がある。

## 検証結果（検証サーバ 192.168.3.240・2026-11-08。途中経過）
- ログインの有効性（作成時の MAC を固定して確認）: AdGuard VPN の H1・H2、ProtonVPN の H1 が有効。ProtonVPN の H2 は未確認。
- **異なるプロバイダの 2 段（入口 AdGuard VPN JP → 出口 ProtonVPN US）: 成立。** 出口の外部からの IP は Seattle（US）で、入口の tun0 の受信バイト数が増えたことで、経路を通ったことを確認。
- **MTU**: 出口の ProtonVPN の MTU を 1420（既定の WireGuard 相当）に上げても、2 段の経路で DF 付き ICMP のペイロード 1392 が通った。
- **3 段（出口 ProtonVPN US → 中段 AdGuard VPN JP → 最外段 AdGuard VPN DE）: 成立。** 出口の外部 IP は 3 回とも Seattle（US）。両方の AdGuard の tun0 に受信が届くことを確認。
  - 成立の条件: 最外段を先に接続し、中段の既定経路を最外段へ向けてから中段を接続する。中段を既定経路が向いた状態で接続し直すと、中段のトンネルが再接続のまま止まった（前回の失敗の原因。状態表示と tun0 の不一致が出た）。
  - 3 段の経路での DF 付き ICMP は、ペイロード 1392（出口の MTU 1420 相当）まで通った。
  - 途中で 1 回、TLS の途中切断（EOF）が出たが、同じ取得を繰り返すと成功した。大きい転送での安定性は未確認。
- ログイン有効は 4 本（AdGuard VPN H1・H2、ProtonVPN H1・H2）。5 本目として AdGuard VPN の新しい端末（H3、MAC `02:42:ac:11:00:22`）を登録し、ログインを確認した。
- **同時接続 5 本（上限）で成立**: 3 段 A（ProtonVPN H1 US → AdGuard H1 JP → AdGuard H2 DE）と、2 段 B（ProtonVPN H2 CH ← AdGuard H3 JP）を同時に張った。5 本の tun0・proton0 はすべて存在。出口の IP は A が Seattle（US）、B が Zurich（CH）。
- 2 段 B の ProtonVPN H2 の MTU は既定の 1360。A の H1 は 1420 に上げて確認した。B は未調整。
- **MTU の上限（2 段・3 段とも同じ値）**: DF 付き ICMP で、IP のサイズ 1440（ペイロード 1412）まで通り、1440 を超えると通らない。ホストの直接経路は 1472 まで通るため、上限は VPN の段（AdGuard）のオーバーヘッドによる。出口の ProtonVPN の MTU を 1440 に設定した（A は 1420 → 1440、B は 1360 → 1440）。
- **安定性（10 MB を繰り返し取得）— 訂正あり**: 試験スクリプトが取得サイズを検証していなかった。サイズを見直すと、次のとおり。
  - B（2 段、MTU 1440・MSS クランプあり）: 16 回すべて 10485760 バイト（全量）を取得。安定。
  - A（3 段、MTU 1440）: 取得は 4.5〜5.4 MB で途中終了していた（全量ではない）。前回の「A 6/6・10/10 成功」は誤り。A は安定していない。MSS クランプを入れても改善は確認できていない。
- **5 段（出口 PR US ← AG JP ← AG DE ← AG JP ← PR CH）**: 全段の接続とトラフィックの通過は確認。実効 MTU は IP サイズで約 1368（ペイロード 1340 まで通過、1350 から不通）。出口の MTU を 1360 に設定。10 MB の取得は 3 回とも途中終了（約 2.0〜2.3 MB）。安定していない。
- **途中終了の切り分け（2026-11-08）**:
  - 途中終了は、宛先（proof.ovh）が接続の途中で RST を送って切ることによる（FIN ではない）。TCP の再送はほぼ増えていない。
  - 経路の往復時間は段を重ねるたびに増える（ホスト直接 約 42 ms、AG 1 段 約 565 ms、AG 2 段 約 1.1 s、5 段 約 2.4 s）。損失率は 8 秒の待ちでは 0%。
  - 仮説: AdGuard の段のトンネルは TCP 443 で張られている。TCP の上に TCP を重ねると（TCP over TCP）、少しの損失で長く止まり、宛先のタイムアウトで切られる。
  - 検証（10 MB、IPv4 固定）:
    - Proton 同士の 2 段（出口 PR H1 ← 中継 PR H2）: 2/2 全量取得（約 12 秒）。
    - AG 1 段を最外段に置いた 3 段（出口 PR H1 ← 中継 PR H2 ← 最外段 AG H3）: 2/2 全量取得（約 18 秒）。
    - AG を 2 段以上重ねた経路（AG ← AG、5 段）: 途中終了が続く。
  - 注意事項（制約にはしない。利用者の決定）: AG の段を内側に重ねた経路では、長い転送が途中で切れることがある。詳細と検証結果は `.kiro/discovery/multihop-chain-input.md` の section 17 に記録する。
- 検証サーバのディスクは Proxmox で 96G に拡張済み。ルートのパーティションと ext4 を拡張し、94.9G（空き 45G）。

## Open Questions（design 前に決める）
1. 異なるプロバイダの組み合わせの実機検証。AdGuard VPN の段と ProtonVPN の段を、同じ経路表・MTU・インターフェース名の中で共存させられるか（未検証）。
2. 段数 n の上限の値（設定値の既定と最大）。段が増えたときの MTU・遅延・規約上の同時接続数の影響をどこまで許すか。
3. 3 段以上の実機検証（既定経路の連鎖、経路のループ防止、段ごとの MTU の実測）。
4. 本番ゲートウェイ（既定経路が 192.168.3.251 を経由する環境）で、段の追加が本番の通信に影響しないか（実験では本番の経路を変えていない）。
5. ネットワーク障害時の挙動（kill switch と段の失敗の扱いを、実機で確かめる）。
