- [ ] 1. 同梱の座標データを用意する

  - 生成スクリプトが、dbf から国の識別キー・名称・人口・座標・首都の区分を抜き出し、同梱データを書き出す
  - 入力の zip の SHA-256 と件数（7,342）を、生成結果に記録する
  - 観測できる完了条件: 生成した同梱データの件数が 7,342 件で、生成結果の出力に同梱データの容量（実測値）が含まれている
  - _Requirements: 3.4_

- [x] 1.2 同梱データを型付きで読み込む
  - 同梱データを一度だけ読み、国の首都の区分（区分 0・1）と、区分 alt を除外した記録を型付きで提供する
  - 件数と行の形を検査してから型を付ける（JSON の型推論のままでは使えないことを、PoC で確認済み）
  - 形式が想定と違えば起動時に失敗する
  - 観測できる完了条件: 単体テストで、件数・東京の首都・コソボの識別キー（KOS）が読み込まれ、形式不正のデータで起動が失敗することを確認できる
  - _Depends: 1.1_
  - _Requirements: 3.1, 3.2, 3.4_

- [ ] 2. 座標の計算と照合の規則を作る
- [x] 2.1 (P) 大圏距離と表示用の丸めを作る
  - 二点の地球表面上の距離（km）を計算する。同一点は 0、入れ替えても同じ値になる
  - 表示用に、小数点以下第一位へ丸める
  - 観測できる完了条件: 単体テストで、東京–大阪が 396.4 km、同一点が 0、対称性を満たし、丸めが小数点以下第一位で行われる
  - _Boundary: Great circle_
  - _Requirements: 4.1, 4.2, 4.3_

- [x] 2.2 (P) 国の首都と都市の座標を照合する
  - 国の首都は、区分 0 の記録のうち人口の最も多いもの。無ければ区分 1 のうち人口の最も多いもの。どちらも無ければ引けない
  - 都市は、国の識別キーと都市名（名称・英語名・ASCII 名のいずれか。アクセント・大文字小文字・記号を無視）で照合し、候補が複数なら人口の最も多いものを使う
  - 利用できる国の選択肢を、首都が引ける国に限って名前付きで返す
  - 観測できる完了条件: 単体テストで、東京（JP）・ラパス（BO）・香港（HK）の首都、プエルトリコの首都が無いこと、京都が首都にならないこと、コロンバス（US）がオハイオを選ぶこと、コペンハーゲン（DK）が英語名で一致すること、アシュバーン（US）が無いことを確認できる
  - _Boundary: Geo index_
  - _Depends: 1.2_
  - _Requirements: 3.1, 3.2, 3.3_

- [ ] 3. 距離による並べ替えの規則を作る

  - 入力の配列を変えず、新しい配列と距離（丸め済み）を返す
  - 観測できる完了条件: 単体テストで、先頭配置・距離順・末尾送り・同距離の順序保持・入力の不変を確認できる

## Implementation Notes
- 1.2: JSON の型推論は配列の要素が混在するため、そのままでは型が合わない。読み込み側で件数と行の形を検査してから型を付ける。
- 2.2: `Intl.DisplayNames` は ISO 3166-1 alpha-2 以外のコードで例外を投げる。国の名前は 2 文字の ISO のみに解決し、コソボ（KOS）は個別の名前を持つ。
- 5.3・7.1・7.2: OpenAPI 3.0 は `null` を型として扱えない（生成クライアントに警告が出る）。値が無いときは項目を省く任意項目にする。
- 7.2: 参考一覧の国コードの対応は、プロファイルの最上位の `countryAliases` を使う（距離の注釈と共通）。参考一覧の旧い対応（`availableLocations.countryAliases`）は、`location-city-selection` のタスク 1.2 で移す。
- 8.1〜8.4: 生成クライアントの型は再生成で変わるため、型の検査（web の `tsc`）を各タスクの後に行う。
- 9.1: 中継の転送は `web/server/accept-language-forwarding.test.ts`（HTTP の上流）で確認。本番と同じ TLS 構成（web の undici 設定、API の CA 検証）では、実際の web サーバ（`web/server/index.ts`）を起動し、HTTPS の上流（API と同じ証明書）に対して確認した。ja-JP のヘッダは上流へ届き、ヘッダ無しでは値が付かなかった。誤った CA では UNABLE_TO_VERIFY_LEAF_SIGNATURE で 502 になり、検証が効いていることを確かめた（手順は調査メモ research.md に記録）。
- 9.2: 全体のテスト（proxy 293・api 444・web 255・server 2）、中立性の検査、インストーラの検査、API の lint、ビルドはすべて通過。
