# Implementation Plan

> 前提（他の仕様の完了）: 本 spec は `location-distance-sort` の次の成果に依存する。実装の前に完了していること。
> - 2.2: 国の首都と都市の座標の照合（`getGeoIndex`）
> - 4.1: ping 計測の可否（`isPingMeasurable`）
> - 4.2: 国コードの対応（プロファイルの最上位の `countryAliases`）
> - 6.1: 行の距離の注釈（`annotateDistances`）

- [ ] 1. プロファイルの宣言を整える
- [x] 1.1 都市の一覧とサーバ一覧の宣言を、プロファイルに追加する
  - プロファイルの宣言に、都市の一覧の取得（国ごと）・サーバ一覧キャッシュの項目名・サーバ名での接続の引数を書けるようにする
  - ProtonVPN の宣言に、`cities list` の取得、サーバ一覧（`VPN/serverlist.json`、`LogicalServers`）の項目（サーバ名・国・都市・Tier・Features・Status・Score・Load）、接続の引数 `connect %LOCATION%`（サーバ名）を書く
  - 観測できる完了条件: プロファイルの検証の単体テストが通り、ProtonVPN の宣言が読み込まれ、AdGuard VPN の宣言は変わらない
  - _Boundary: Profile declaration_
  - _Requirements: 5.1, 5.6, 6.1, 6.3_

- [x] 1.2 参考一覧の国コードの対応を、プロファイルの最上位の対応へ移す
  - 参考一覧が読む国コードの対応を、プロファイルの最上位の `countryAliases` から読むように変える。ProtonVPN の宣言の参考一覧側の対応は削除する
  - 観測できる完了条件: 既存の参考一覧の単体テストと統合テストが変更なしで通り（UK が GB として名称解決される）、距離 spec の注釈と同じ対応を使う
  - _Boundary: Plan list API_
  - _Depends: 1.1_
  - _Requirements: 5.1_

- [ ] 2. 純粋な解析と規則を作る
- [ ] 2.1 (P) 都市の一覧の表を解析する
  - 「Cities in <国名>:」の見出しに続く表（City・Features）から、都市名を表の順に取り出す。重複は除く
  - 都市名に空白を含むもの（Phnom Penh）を正しく読み、空行や案内文は読み飛ばす。見出しが無いときは例外にする
  - 観測できる完了条件: 単体テストで、空白を含む都市名、重複の除去、見出し無しの例外を確認できる
  - _Boundary: City list parser_
  - _Requirements: 5.1_
  - _Blocked: ProtonVPN の cities list の実出力を確認できない（検証サーバでサインインが必要。`protonvpn cities list JP` は「Authentication required」で失敗）。表の中の案内文を都市と区別する規則の根拠が無く、レビューで差し戻された。実出力を確認してから規則を決める。作業ツリーの city-list-parser.ts は未コミット_

- [x] 2.2 (P) サーバ一覧キャッシュから、都市のサーバと最速サーバを選ぶ
  - サーバ一覧キャッシュを宣言に従って読み、有効かつ Secure Core（Features の bit 1）でないサーバを、都市ごとに Score の小さい順に並べる。同じ Score は名前の昇順にする
  - 都市の最速サーバ（Score が最小のもの）を返す。Tier 0 を無料、それ以外を有料として表す
  - 読み取りに失敗したとき、空の一覧にせず例外にする
  - 観測できる完了条件: 単体テストで、Secure Core と無効なサーバの除外、Score 順と同値の決定的な順序、最速サーバの選択を確認できる。実データ（ProtonVPN の VPN/serverlist.json の Chicago）から、有効かつ非 Secure Core のサーバを Score の小さい順に並べ、最速（Score が最小）を選ぶ。テストは実データを使い、Score が最小のサーバが選ばれることを確かめる。サーバ名の固定値は、データの更新で変わるため条件に書かない
  - _Boundary: Server catalog_
  - _Requirements: 3.1, 3.4, 5.6, 6.1_

- [x] 2.3 (P) サーバの接続先 ID を作り、既存の ID の検査を広げる
  - サーバの ID を、`srv-` の接頭辞と、サーバ名を小文字にし `#` を `-` に変えた値で作る（例: `CH-US#13` → `srv-ch-us-13`）
  - 接続先の ID の検査が、都市の ID（国コード・都市のスラッグ）とサーバの ID の両方を受け付けるようにする
  - 観測できる完了条件: 単体テストで、両方の形式が通り、他の形式（空・大文字・長すぎる値）が拒否されることを確認できる
  - _Boundary: Location id_
  - _Requirements: 4.4, 4.7_

- [x] 2.4 (P) 国の行を組み立てる
  - ProtonVPN は国の表から国の行を作り、AdGuard VPN は都市の行から国の行を作る（国ごとに、都市の ping の最小値を持つ）
  - ping を計測できるときは、国の行を都市の ping の最小値の小さい順に並べる。国の行には ping の値を出さない（並べ替えの根拠としてだけ使う）
  - 観測できる完了条件: 単体テストで、両プロバイダの国の行の組み立て、国の行の ping が最小値になること、ping 計測可の並び順、国の行に ping の値を含まないことを確認できる
  - _Boundary: Location tree_
  - _Requirements: 7.1, 7.2, 7.6_

  - 観測できる完了条件: スキーマの単体テストで、距離が任意の項目として含まれ、既存の国の行の項目（国・名前・ping・お気に入り・前回接続）が変わらないことを確認できる

## Implementation Notes
- 2.2（サーバ一覧）: 実データ（検証サーバの ProtonVPN `VPN/serverlist.json`）では `Status` は真偽値、Secure Core は Features の値 1 で判定する。例は規則の記述に改めた（2026-11-08、利用者の判断）。
- 3.3（お気に入りの保存）: タスク 5.5 で既存ルート（api/src/routes/connection-locations.ts の登録）を、表示名（種類・国・国名・都市・サーバ名）付きの登録に置き換え、ID から表示名を推定する互換処理（favorite-locations-store.ts の addFavoriteLocation）を廃止すること。推定した国名・都市名は暫定の値。
- 4.1（接続先の解決）: 一覧外お気に入りのプロバイダ別の挙動と provider の値は、ベンダー中立性を保つためプロファイルの `locationTarget` 宣言で指定する。`api/src` の型にはベンダー固有名を含めない。設計の ConnectTarget の `provider` は string（宣言の値）とし、ベンダー名のリテラルは使わない（2026-11-08 の利用者の判断。禁止語は vendors の宣言から自動で作られるため、リテラルを入れると check:neutrality が失敗する）。
- 5.4（Locations API）: GET /v1/connection/locations は設計どおり平らな一覧から国行へ変更した。6.7 の画面差し替えまで既存 web 画面とは応答契約が一時的に不整合となる。web の既存テスト成功は API 統合時の互換性を保証しない。このブランチを本番へ出す前に、6.7 までを完了させること。
- 6.2（戻るボタン・タブの行・右スワイプ）: 部品（web/src/locations/LocationBackBar.tsx）を作った。一覧画面への組み込みは 6.7。実機のスワイプとブラウザのポインタキャプチャの再配送は未確認（jsdom では検証できない）。残るリスクとして、6.7 の後に実機で確認する。
