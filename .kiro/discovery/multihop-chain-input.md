# 多段接続（2 段・ベンダー非依存）の discovery 入力

このファイルは、次の discovery セッションが最初に読むための入力です。決定事項・調査結果・未確定の事項・実験の手順をまとめます。

## 1. 決定済みの方針（利用者の回答）

- 対象: 全ベンダーに同時に適用する（仕組みは共通）。
- 段数: 2 段（入口→出口）のみ。
- ベンダーの既存の Secure Core 機能（Proton の `--securecore` など）: 置き換える。ベンダー機能は使わず、移行後に削除する。
- 入口の選び方: 利用者は出口の国を選ぶ。入口は自動で決める。入口の国は利用者が任意に変更できる。自動で決める方法は複数用意する（具体的な方法は未定）。
- 実現方式: 段ごとに別のネットワーク空間（コンテナ）を用意し、後段は前段のトンネル経由で接続する。

## 2. 現在の構成の制約（調査結果）

- ゲートウェイ（`proxy`）とランナー（`runner-protonvpn`・`runner-adguardvpn`）は、すべて `network_mode: host`。経路表と nftables を共有している。
- トンネルは 1 本を前提にしている（`vpnIface` は 1 つの文字列。出口の検出は 1.1.1.1 への経路で 1 つ）。
- ランナーは 1 ベンダーに 1 つ（サービス名・ソケット・ログインの状態が、ベンダー ID に紐づく）。
- 接続状態は 1 つのプロバイダに 1 つ。API の接続は、プロバイダ 1 つと接続先 1 つを受け取る。
- プロファイル（`vendors/*/profile.json`）に、多段接続の宣言はない。
- ProtonVPN の起動処理は、`proton[0-9]+` の名前のインターフェースを起動時に消す。2 本目の Proton トンネルと干渉する。
- 権限: ゲートウェイとランナーは `NET_ADMIN`。AdGuard のランナーは `/dev/net/tun` と sudo が必要。

## 3. 実現性の調査（サブエージェントの報告の要点）

判定: **条件付きで技術的には可能。ただし、規約と同時接続数が未確定。**

技術面の条件:
1. 2 段目のエンドポイント宛ての経路を固定する（経路のループを防ぐ。fwmark か経路の固定）。
2. MTU を下げる（1420 から約 60 バイト差し引く。計算値。未確認）。
3. コンテナ内の D-Bus と NetworkManager の版を固定する（既知の問題が多い）。
4. 非 host 化は、ゲートウェイの名前空間の付け替えを含む大きな変更。以前の bridge 方式では、AdGuard のログインが失効した（`vendors/adguardvpn/compose.yml` のコメント）。

規約・権限・ライセンス（未確定）:
- **Proton**: 同時接続数の上限は、公式規約に記載がない（第三者記事では無料 1・有料 10。未確認）。無料プランでは 2 段は成立しない。
- **AdGuard**: EULA が「同時に接続するインスタンス数」を制限しうると明記。無料は同時 2 台、Unlimited は同時 10 台（公式 KB）。2 段は 2 インスタンスを消費する。
- **包括的な禁止条項**: 両社とも「認められていない用途」を禁止。VPN チェーンを明示的に禁止する文言は、見つからなかった。
- **AdGuard CLI**: オープンソースではない（商用 EULA）。イメージをレジストリに公開すると、EULA §4.1 との関係で問題になりうる。
- **Proton CLI**: 公式リポジトリは取得できず、ライセンスは未確認。NetworkManager ライブラリは GPL-3.0 で、旧版扱い。
- **保守**: AdGuard CLI は活発（最新 1.8.2。リポジトリは 1.7.12 に固定）。Proton CLI 1.0.5 は Proton の apt リポジトリから配布。

## 4. 検証サーバの現在の状態（実験前の確認。読み取りのみ）

- ディスク: 75%（空き 15GB）。
- ホストに tun・proton・wg のインターフェースはない。既定経路は `enp6s18`。
- AdGuard のランナー: 切断済み（`VPN is disconnected`）。ログインの状態はランナーの volume にある。
- 稼働中のコンテナ: `vpngwgui-{api,proxy,web,runner-protonvpn,runner-adguardvpn}-1`。
- sudo は利用できる。`ip netns` は利用できる。

## 5. 実験の手順（未実施）

目的: 同一の有料アカウント（または 2 つのデバイス）で 2 本のトンネルを同時に張れるか。2 段目の通信が 1 段目を経由して、出口の IP を変えるか。

前提（利用者の操作が必要）:
- AdGuard: 実験用のデバイスとして、ログインを 2 回行う（既存のランナーの login 状態は複製しない）。ログインは利用者が、表示された URL とコードで行う。
- ProtonVPN: 2FA を含むログインが必要。AdGuard の結果を見てから行う。

手順（すべてホストの経路を変えない。`ip netns` で分離する）:
1. 名前空間 `exp1`・`exp2` を作る。各名前空間で、AdGuard の CLI を別々のデータディレクトリ（`HOME`）で動かす。
2. `exp1` で接続し、egress の IP を確認する。
3. `exp2` で接続し、egress の IP を確認する。両方が接続中か、同時に成立するかを見る（インスタンス数の扱い）。
4. 2 段目（`exp2`）の既定経路を `exp1` の内側（veth 経由）に向ける。`exp2` の接続が成立するか、egress の IP が変わるかを確認する。
5. 大きいパケット（MTU 1420 の境界）が通るかを確かめる。
6. 後始末: 両方を切断する。名前空間とデータディレクトリを削除する。デバイス登録の解除は、利用者が行う。

判定基準:
- 同時接続が 2 本とも成立する → 規約とは別に、技術面は成立。
- 2 段目の egress IP が、2 段目の出口の国になる → 多段の経路は成立。
- どちらかが失敗する → 失敗の内容（インスタンス上限、経路、MTU）を記録し、方式を見直す。

中止の条件:
- 検証サーバの他のプロジェクトの通信に影響する兆候が出たら、直ちに中止し、名前空間を削除する。
- AdGuard のランナーのログインが失効したら、中止して利用者に報告する。

## 9. 実験の結果（AdGuard VPN・2026-11-08 実施）

結論: **ネットワーク名前空間の中で AdGuard VPN の CLI を動かすと、デバイスのログインが失われる。** 2 本のトンネルの同時接続までは到達できなかった。

経過:
1. 実験用に、AdGuard VPN のデバイスを 2 つ登録した（利用者の操作）。どちらもログイン済み（Premium・同時接続 10 台まで）。
2. 名前空間 `exp1` を作り、NAT で外へ出した。名前空間の外からの出口 IP は、ホストと同じだった（ホストの経路は変えていない）。
3. 名前空間の中で `connect -l JP` を実行したところ、デバイス 1 のログインが失われた。
4. 再登録したデバイス 1b も、名前空間の中で CLI を一度動かすと失われた。
5. ホスト名 `aitest` が名前空間の中で解決できない問題（sudo の失敗）は、`/etc/netns/exp1/hosts` で直した。それでも、デバイス 2 は名前空間の中の読み取り（`license`）の 1 回で失われた。
6. 運用中のランナーのログインは、最後まで有効だった（別のコンテナ・ホストのネットワーク）。

判断:
- 段ごとに別のネットワーク空間（案 A）は、AdGuard VPN の CLI では成立しない可能性がある。原因は未確定。仮説は次の 3 つ（詳細は下の「原因の仮説」）。
  - H1: サーバ側で、名前空間の中の接続を別のデバイスとみなし、既存のトークンを無効化した。
  - H2: CLI がローカルの暗号化された設定を読めず、ログイン状態を消した。
  - H3: CLI が異常を検知し、サーバ側でトークンを失効（revoke）させた。
- 同じ現象は、リポジトリの `vendors/adguardvpn/compose.yml` に記録されている（Docker ブリッジへの変更で、コンテナ再作成のたびにログインが失効）。
- 未確認: 名前空間の中で同じ端末の識別子（MAC・ホスト名・machine-id）を再現すれば回避できるか。LXD など別の仮想マシンなら可能か。Proton VPN の CLI で同じ現象が起きるか。

後片付け（済）:
- 名前空間 `exp1`、veth、NAT のルール（`10.200.1.0/24`）、`/etc/netns/exp1` を削除した。
- 実験のデータ（トークンを含む）を削除した。エラーの抜粋（秘密情報は伏せた）は `~/exp-adguard-archive/` に残した。
- 利用者にお願いすること: AdGuard VPN のデバイス一覧から、実験で登録した 3 つ（ログインの失われたもの）を削除する。

次のセッションでの判断事項:
1. 案 A を捨て、案 B（ホストの空間の中で順に接続し、経路で制御）を検討するか。
2. 案 A を残し、LXD などの仮想マシンで再実験するか。
3. Proton VPN でも同じ現象が起きるかを、先に確かめるか。

## 10. 原因の仮説（未確定）

確認できた事実:
- 名前空間の中で CLI を動かした後、そのデータディレクトリでは、通常の環境でも「ログインしていない」になった。
- ログインのデータ（`adguardvpn-cli.conf`）は暗号化されていて、中身は読めない。
- 運用中のランナーのログインは、別のコンテナで動いており、最後まで有効だった。
- ネットワークの IPv6 のエラー（Network unreachable）は、名前空間の外の通常の実行でも出ていた。このため、IPv6 は直接の原因ではないと考えられる。

バイナリの文字列から分かること（推測の材料。動作の証拠ではない）:
- 設定の暗号化（ConfigEncryptor）と、マシン ID（`/etc/machine-id`・`/var/lib/dbus/machine-id`）の参照がある。
- トークンを無効化する API（`/api/ev1/revoke_token`、RevokeAccessToken）がある。
- ネットワークのインターフェースの MAC アドレスやホスト名を識別子として使う文字列は見つからなかった。

仮説の検討:
- H1（端末の識別の変化）: 名前空間を「別の端末」とみなしたなら、アカウントのデバイス一覧に新しい項目が増えるか、既存の項目が消えるはず。
- H2（ローカルの復号の失敗）: 復号できなければ、ローカルのログイン状態が消える。ただし、マシン ID は名前空間でも同じなので、マシン ID だけでは説明できない。
- H3（CLI によるトークンの失効）: CLI の revoke API が呼ばれたなら、サーバ側でもログインが無効になる。運用中のランナーの影響がないことと矛盾しない。

確認に必要なこと:
- AdGuard VPN のアカウントの Web の画面で、デバイスの一覧を見る。今日の 06:40〜06:50 頃に登録したデバイス（デバイス 1・1b・2）が残っているか、消えているかを確認する。
- 「ライセンス」の出力には、デバイスの数は出ない。「同時接続 10 台まで」は、プランの上限であり、登録の数ではない。

## 13. 対照実験（マーカー方式・2026-11-08 実施）

目的: 名前空間の中の CLI の実行が、ログインを失わせるかを、1 回だけの読み取りで確かめる。

手順と結果:
1. 通常のホスト環境で、機器のログインを 1 回行った（デバイス 3）。アクティビティの最上部に、新しいログインが 1 件追加された（記録されることは確認済み）。
2. 名前空間 `exp1`（IPv6 を無効化、ホスト名の解決を設定済み）の中で、`license`（読み取りのみ）を 1 回実行した。結果: 「ログインしていない」。
3. 同じデータで、ホストの通常環境から `license` を実行した。結果: 「ログインしていない」（ログアウトは持続）。

ログの観察（秘密情報は伏せた）:

## 14. Docker での切り分け（マーカー・MAC 固定・退避と復元・2026-11-08 実施）

前提: 本番と同じイメージ（`vpngwgui-runner-adguardvpn`）、ブリッジのネットワーク、ホスト名 `aitest`、データは専用のボリューム。ホストの経路は変えていない。

結果:
1. 機器のログイン（MAC A = `02:42:ac:11:00:20`）→ 有効。
2. 同じ MAC で作り直し（同じボリューム）→ 有効。
3. MAC だけを B（`02:42:ac:11:00:99`）に変えて作り直し → **ログアウト。** 設定ファイルは 537 バイトから 175 バイトに書き換わっていた（ローカルのログイン情報が消えた）。
4. 退避しておいた設定を戻し、MAC A で確認 → **有効に戻った。** サーバ側のトークンは失効していなかった。

判断:
- ログインの喪失は、サーバ側の失効ではなく、CLI がローカルのログイン情報を破棄したことによる（H2 を支持。H3 は支持されない）。
- 破棄の引き金は、MAC アドレス（または、そのインターフェースの識別）の変化。ホスト名・ボリュームは同じだった。
- 本番のランナーが `network_mode: host` で安定しているのは、MAC が変わらないため（ホストの NIC の MAC のまま）。リポジトリのコメント（ブリッジに変えると再作成のたびに失効）とも一致する。
- 名前空間の試験で起きたログアウトも、同じ仕組みで説明できる（名前空間の veth は、ホストと別の MAC を持つ）。
- LXD（仮想マシン）も、別の MAC を持つため、そのまま使うと同じ問題が起きると考えられる。対処は、LXD の有無より、「ログインを作ったときの MAC を、以後も固定すること」が本質。

次の検証（案）:
- 2 本目のデバイスをログインし、各段のコンテナに、ログインした時の MAC を固定して割り当てる。2 段を Docker のネットワークで接続し、2 本の同時接続と、2 段目の出口 IP を確かめる（案 A の Docker 版）。

後片付け:
- 検証用のボリューム `aglogin-test`（ログアウト済み）と `aglogin-test2`（ログイン済み）は、次の検証まで残す。不要になったら削除する。
- 退避した設定ファイル（トークンを含む）は削除した。

## 15. AdGuard VPN の 2 段接続（Docker・2026-11-08 成立）

## 16. Proton VPN の 2 段接続（Docker・2026-11-08 成立）

構成: 本番と同じイメージ（`vpngwgui-runner-protonvpn`）。ネットワーク `chain-pr`（172.31.20.0/24）。
- H1（MAC `02:42:ac:11:00:30`・ボリューム `aproton-p1-*`・IP 172.31.20.10）: JP#300（Tokyo）に接続。iptables の NAT で `chain-pr` の通信を中継。
- H2（MAC `02:42:ac:11:00:31`・ボリューム `aproton-p2-*`・IP 172.31.20.20）: 既定経路を H1 へ向けてから、US-WA#311（Seattle）に接続。

結果:
1. H2 の通信は、接続前の時点で H1 の Proton トンネルを通った（H1 の出口 IP と一致）。
2. H2 の接続後、出口の国は US（地理情報で確認）。
3. H2 の通信は H1 の NAT を通った（MASQUERADE のカウンタが増えた）。
4. H1 は JP のまま。両方とも同じアカウントで、同時にログインしている。

補足:
- 中継する通信は、fwmark のない通信として Proton の経路表を使う（`ip rule` の `not from all fwmark ... lookup ...`）。これにより、中継の通信も H1 のトンネルを通る。
- Proton の既存の Secure Core（入口が CH/IS/SE などの Proton 所有サーバに限られる）とは異なり、この方式は任意の国の組み合わせ（JP→US）で動いた。

まとめ（discovery への入力）:
- AdGuard VPN と Proton VPN の両方で、Docker による 2 段接続が成立した。
- 成立の条件は、各段の MAC アドレスを、そのデバイスのログインを作ったときの値に固定すること（section 14）。
- 中継は、NAT（MASQUERADE）と既定経路の向きで実現できる。段ごとのネットワーク（bridge）で、ベンダーの CLI を動かせる。
- 未確認: ホストの既定経路が本番ゲートウェイ（192.168.3.251）を経由する状態での、本番の通信への影響（今回は変更していない）。段数を 3 以上にした場合。異なるベンダーを混ぜた場合（AdGuard の段と Proton の段）。ネットワーク障害時の挙動（kill switch）。

## 17. 検証サーバでの段数と安定性（2026-11-08 実施）

目的: 段数（同時接続 5 本まで）と、長い転送の安定性を確かめる。

### 17.1 接続と経路（成立）
- 5 段（出口 PR H1 US ← AG H1 JP ← AG H2 DE ← AG H3 JP ← PR H2 CH）: 5 本すべてのログインを 1 本の経路で使い、接続し、全段のトンネルで受信を確認した。出口の外部 IP は US（Seattle）。
- 3 段（PR H1 US ← AG H1 JP ← AG H2 DE）・2 段（PR H2 CH ← AG H3 JP）・2 段（PR H1 US ← AG H1 JP）も成立（以前の確認と同じ）。
- 最外段に Proton を置く場合も接続できる（iptables の NAT と既定経路の向きを、中継の Proton コンテナに設定）。

### 17.2 MTU（経路の実効上限）
- 3 段・2 段とも、DF 付き ICMP で IP サイズ 1440（ペイロード 1412）まで通る。出口の proton0 を 1440 にできる。
- 5 段では、IP サイズ 1368（ペイロード 1340）まで通り、1350 から通らない。出口の proton0 を 1360 に設定した。
- 段の数が増えるほど、経路の MTU は下がる（AG の段のオーバーヘッドによる）。ホストの直接経路は 1472 まで通る。

### 17.3 長い転送の途中終了（注意事項。制約にはしない）
- 症状: 10 MB の取得が途中で終わる（AG 2 段以上を重ねた経路で発生。5 段で 3 回とも約 2.0〜2.3 MB で終了）。
- 途中終了は、宛先（proof.ovh）が接続の途中で RST を送って切ったもの。FIN ではない。TCP の再送はほとんど増えていない。
- 往復時間は段を重ねるたびに増える: ホスト直接 約 42 ms、AG 1 段 約 565 ms、AG 2 段 約 1.1 s、5 段 約 2.4 s。損失率は 8 秒の待ちでは 0%（1 秒の待ちでは応答を取りこぼした。遅延による）。
- AG のトンネルは TCP 443 で張られている（TCP の上に TCP が重なる）。
- 仮説: AG のトンネルを内側に重ねると、TCP over TCP で損失時に長く止まり、宛先のタイムアウトで切られる。
- 検証（10 MB を IPv4 固定で取得）:
  - Proton 同士の 2 段（出口 PR H1 ← 中継 PR H2）: 2/2 全量取得（約 12 秒）。
  - 3 段（出口 PR H1 ← 中継 PR H2 ← 最外段 AG H3）: 2/2 全量取得（約 18 秒）。
  - AG を 2 段以上重ねた経路（AG ← AG、5 段）: 途中終了が続いた。
- MSS クランプ（中継の FORWARD で `TCPMSS --clamp-mss-to-pmtu`）は、AG ← AG の経路では改善を確認できなかった。
- 試験の注意: 初期の試験スクリプトは取得サイズを確認していなかった。途中終了を「成功」と数えていた（A 経路の「10/10 成功」は誤り）。サイズを確認する版で試験し直した。
- 扱い: 要件の制約にはしない（利用者の決定）。段の置き方（AG を内側に重ねない等）は、必要になれば別途検討する。

### 17.4 検証環境の注意
- 検証用コンテナ・ネットワーク（vh-*、chain-*）は検証のために残している。終わったら片付ける。
- 検証サーバのディスクは Proxmox で 96G に拡張し、ルートのパーティションと ext4 を拡張済み（94.9G）。
- AdGuard の検証ログ（各ボリュームで約 100MB）と、前回の実験で登録した AdGuard の端末の整理が残っている（端末の削除は利用者が行う）。
