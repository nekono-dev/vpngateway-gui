# WBS（作業分解構成）について

`specs/` が「最終形として何を作るか」を定義するのに対し、このディレクトリは「どの順番で作るか」を定義する。各フェーズは前フェーズの成果物の上に積み上げる形とし、フェーズ単独でdocker-composeによる動作確認ができる状態を維持する。

各`phaseN.md`は以下の構成で記載する。

- **目的**: このフェーズで何を達成するか
- **前提**: 開始前に完了している必要がある前フェーズ・決定事項
- **スコープ外**: このフェーズでは意図的に行わないこと（後続フェーズとの境界を明確にするため）
- **主要タスク**: 実施する作業項目
- **完了基準**: docker-compose等で確認可能な具体的な合否判定方法
- **次フェーズへの申し送り**: 実装中に判明した制約・設計上の留意点

各`phaseN.md`の「主要タスク」はチェックボックス（`- [ ]`）形式で記載し、該当タスクを実施した際は`specs/`配下の`tasks.md`と同様にチェック（`- [x]`）を入れること。

フェーズ一覧の「状態」欄は「実装完了」と「検証完了」を分けて記載すること。コード実装が主要タスクを満たしていても、実機・実データでの動作確認（完了基準）が済んでいない場合は「実装完了・検証待ち」のように限定を明記し、単に「完了」と書かない（2026-09-14、`c5c3eb5`のコミットメッセージ「phase2の実装完了」が実機接続検証待ちの状態を指していたことによる誤解を教訓に追記）。

## フェーズ番号＝実施順（2026-09-22正規化）

**フェーズ番号は実施順そのものである。** 番号の昇順に実施し、フェーズ間の前後関係を示す別建ての「実施順」リストは持たない。

- 新しい要件が判明した場合は、既存フェーズの番号を並べ替えたり途中に挿し込んだりせず、**その時点の最大番号の次の番号**を新フェーズとして`phaseN.md`を追加し、一覧の末尾に積む。実施順は追加後もその番号順のままでよい（挿入したい位置がある場合でも、要件の発生時点では後続フェーズであるため、番号順＝発生順＝実施順は自然に保たれる）。
- あるフェーズの一部タスクを都合により別フェーズより先に実施した場合（例: 後続フェーズ予定だった変更を前倒しで実施）でも、フェーズ番号・ファイル名は変更しない。経緯は該当フェーズの本文（「前提」または「次フェーズへの申し送り」）に記録する。
- 本節より前の版では「フェーズ番号は識別子であり実施順ではない」とし、番号とは別に実施順を文章で管理していたが、WBSの肥大化に伴い両者が食い違いやすく、追跡コストが高くなったため、2026-09-22に番号と実施順を一致させる形へ正規化した（旧番号との対応は本コミットの差分を参照）。

## フェーズ分割の考え方

- 各フェーズ終了時点でできるだけ「実運用に近い状態」で動作確認したいため、実VPNベンダーCLI（例: AdguardVPN CLI）への置換をPhase2に前倒しする（2026-09-06、当初計画から改訂）。当初は「ネットワーク制御ロジック（nftables・3proxy）をモックCLIの決定的な状態遷移で先に検証しきってから、実CLIの非決定的な挙動に対応する方が切り分けが容易」という理由で実CLI統合を最後方（旧Phase4）に置いていたが、この順序だとPhase2・Phase3の時点ではモックCLIの疑似的な挙動でしか動作確認できず、フェーズごとの「動作確認できた」が実運用の裏付けにならない。実CLIの非決定的な挙動への対応自体は、後続のネットワーク制御ロジックと切り離してPhase2単体で先に検証できるため、切り分けの容易さを損なわずに前倒しできると判断した。
- Phase2（実CLI統合）は`network_mode: host`への移行を伴わない。実CLIがトンネルを確立するために`cap_add:[NET_ADMIN]`・`devices:[/dev/net/tun]`は必要だが、これはコンテナ自身のネットワーク名前空間内で完結する権限であり、通常のDockerブリッジネットワークのままで付与できる。LAN機器へのゲートウェイ提供（透過ゲートウェイ・明示的プロキシ）にのみhostネットワークが必要なため、hostネットワークへの移行はPhase3に残す。
- Phase3とPhase6は両方とも`network_mode: host`への移行を前提とする（design.mdより、透過ゲートウェイは`tun`等のトンネルIFへの到達に、明示的プロキシもLAN側インターフェースへの直接bindにhostネットワークを要求する）。移行コストを1回にまとめるため、ネットワーク基盤移行はPhase3にまとめて実施し、Phase6はその上に3proxyを追加するだけにする。Phase3・Phase6はPhase2で統合済みの実CLIが確立する実際のトンネルインターフェースを用いて検証するため、モックの疑似的なIF名生成には依存しない。
- Web UI完成（Phase4）は当初、対応するAPI機能（ログイン代行＝Phase2、ユーザ向け設定の実反映＝Phase3/6）が揃った後に着手する計画だった（先にUIだけ作ると、モック段階の暫定APIレスポンス形状に引きずられて手戻りが生じるため）。
- 【2026-09-21改訂】簡易機能版のプロトタイプとして早期に通し利用できる状態を優先し、Phase4をPhase3（実装完了）の直後・Phase6より前に前倒しする。前倒しの可否判断は以下の通り。
  - 当初の懸念（暫定APIレスポンス形状への引きずられ）は、実CLI統合（Phase2）・設定反映（Phase3の`POST /settings`）が実装済みで、`GET /v1/connection`・`/config`・`/log`の形状が実機検証を経て安定しているため、透過ゲートウェイ関連については解消している。
  - 未実装で依存が残るのは明示的プロキシ（Phase6）と`excludedDomains`（Phase14）のみ。これらは設定ダイアログで編集・保存はできるがproxyへ反映されないため、UIに「未対応」の暫定表示を出し、Phase6/Phase14で実装した時点で実状態表示へ置き換える（`phase6.md`に置換タスクを追加）。
  - 透過ゲートウェイ稼働状況を表示するため、Phase4内でproxy `GET /status`・api `GET /v1/connection/gateway`を新設する（Phase3で未整備だった読み取り経路の補完）。レスポンスはPhase6で`explicitProxy`を追加できる形にする。
  - phase15.mdに残るUI関連項目（認証UI・多言語対応・WebSocket通知）は、LAN限定・認証なしのプロトタイプ運用に不要なため前倒し対象に含めない。
- 【2026-09-21追記】Phase3の実機検証はLXC検証環境＋実VPNで実施済み（`phase3.md`「検証手法」「検証結果」）。上記の判断（未検証のままPhase4へ進む）は結果的に解消した。

- 【2026-09-21追記】Proton VPN対応を、プロバイダ抽象化基盤（Phase 7）とProton VPN固有の対応（Phase 9）に分ける。Proton VPN無料版は接続先を選べない等の制限があり、AdGuard VPN無料版にも制限があるため、特定プロバイダに依存しない「操作の実行可否によるUI制限」の仕組みが要る。これをProton VPN実CLIの導入（NetworkManager等を要する実行基盤のPoCを含み、不確実性が大きい）と切り離すことで、(1)基盤をモックプロバイダCLIで決定的に検証でき、(2)Proton VPN側で実行基盤が成立しない場合でも基盤（Phase 7）の成果が無駄にならず、(3)phaseごとのcommitと検証状態の区切りを明確にできる。詳細は`phase7.md`・`phase9.md`。
- 【2026-09-21追記】Proton VPNの実行基盤のPoC中に、利用者から「Web UIから使うベンダーを選びたい」という要望があり、「ベンダーごとに別のproxyコンテナ」という前提が成り立たなくなった（複数ベンダーのCLIへ同時に到達でき、ネットワーク制御の所有者が1つでなければならない）。そこで、ネットワーク制御（`proxy`）とベンダーCLIの実行（`runner-<ベンダー>`）を分離するPhase 8を新設し、Phase 9（Proton VPN）はその上に`runner-protonvpn`を追加する形へ改訂して、Phase 8の後に実施する。Phase 8はAdGuard VPN実CLI＋Phase 7のモックプロバイダで検証できるため、Proton VPNの不確実性（実行基盤のPoC・有料/無料アカウント）から切り離せる。

## 各フェーズの検証手法（2026-09-21追記）

- 各フェーズの完了判定は、単体テストに加えて、実環境でのE2E検証で行う。検証手順は使い捨てにせず、リポジトリの`e2e/`配下（`e2e/README.md`）にスクリプトとして残し、各フェーズのmdの「検証手法」節に環境・実行方法・結果を記録する。
- Web UIの操作を伴う検証はPlaywrightで行う。実VPN・ネットワークを伴う検証は、KVMが使えない環境ではLXCシステムコンテナ（`security.nesting=true`）で構築した検証環境を用いる。
- 単体テストがスタブに依存する範囲（`nft`/`ip`/`sudo`等）は、実バイナリでのE2Eでのみ検出できる不具合が多い。Phase3ではE2Eにより実装欠陥3件を発見した。
