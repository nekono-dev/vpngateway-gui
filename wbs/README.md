# WBS（作業分解構成）について

`specs/` が「最終形として何を作るか」を定義するのに対し、このディレクトリは「どの順番で作るか」を定義する。各フェーズは前フェーズの成果物の上に積み上げる形とし、フェーズ単独でdocker-composeによる動作確認ができる状態を維持する。

各`phaseN.md`は以下の構成で記載する。

- **目的**: このフェーズで何を達成するか
- **前提**: 開始前に完了している必要がある前フェーズ・決定事項
- **スコープ外**: このフェーズでは意図的に行わないこと（後続フェーズとの境界を明確にするため）
- **主要タスク**: 実施する作業項目
- **完了基準**: docker-compose等で確認可能な具体的な合否判定方法
- **次フェーズへの申し送り**: 実装中に判明した制約・設計上の留意点

## フェーズ分割の考え方

- Phase2とPhase3は両方とも`network_mode: host`への移行を前提とする（design.mdより、透過ゲートウェイは`tun`等のトンネルIFへの到達に、明示的プロキシもLAN側インターフェースへの直接bindにhostネットワークを要求する）。移行コストを1回にまとめるため、ネットワーク基盤移行はPhase2にまとめて実施し、Phase3はその上に3proxyを追加するだけにする。
- Phase4（実VPNベンダーCLI）をPhase2/3より後に置くのは、ネットワーク制御ロジック（nftables・3proxy）をモックCLIの決定的な状態遷移で先に検証しきってから、実CLIの非決定的な挙動（実際のログイン・接続試行）に対応する方が切り分けが容易なため。
- Web UI完成（Phase5）は、対応するAPI機能（ユーザ向け設定の実反映＝Phase2/3、ログイン代行＝Phase4）が揃った後に着手する。先にUIだけ作ると、モック段階の暫定APIレスポンス形状に引きずられて手戻りが生じるため。
