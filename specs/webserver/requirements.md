# 責務の範囲

Webサーバは以下のみを責務とし、業務ロジック（VPN接続状態の判定、コマンド解決、権限チェック等）を一切持たない。

- GUIの表示
- APIサーバへのリクエスト送信（kick）
- 実行結果・状態のユーザ表示
- ブラウザから見て同一オリジンとなるよう `/api/*` をAPIサーバへリバースプロキシすること

また、Webサーバは特定のVPNベンダーに依存しない（`../requirements.md`「ベンダー非依存性」）。ベンダーの名称・ID・出力書式・ベンダーごとの分岐をコードに持たず、ベンダー名はAPIが返す`displayName`を表示するだけとし、機能差はAPIの実行可否（capability）と`loginMethod`に従う（Phase 10）。

# 画面構成

| 画面 | 内容 |
|---|---|
| 接続状態ダッシュボード | 現在のVPN接続状態（接続中/切断/エラー）、接続中のベンダー・国、透過ゲートウェイ／明示的プロキシそれぞれの稼働状況を表示する（設定値ではなく実際の適用状態。`GET /v1/connection/gateway`。Phase 4時点で明示的プロキシは未実装のため「未対応」と表示し、Phase 6で実状態表示に置き換える）。設定ダイアログを開くための設定ボタンを配置する。VPNベンダーへのログイン代行を開始するボタンを配置する（`POST /v1/session`、Phase 2で前倒し実装。`wbs/phase2.md`参照） |
| 接続操作 | 接続先リスト（後述「接続先リスト」。ベンダーCLIが返す接続可能な接続先のみをping値の小さい順に提示し、自由入力は行わない）、接続/切断ボタン、接続中に現在と異なる接続先を選択した場合の「接続先を変更」ボタン（Phase 5）。ベンダー選択は行わない |
| 設定ダイアログ | ダッシュボードの設定ボタンからモーダルダイアログとして開き、APIサーバが保持するユーザ向け設定（`GET`/`PUT` `/v1/settings`）をトグル・テキストボックスで編集する。ページ遷移は行わず、保存はダイアログ内の保存ボタン押下時に一括で `PUT` する |
| 接続ログ | 過去の接続・切断・エラーの履歴表示（APIサーバの監査ログを参照） |

上表は画面の役割の一覧であり、カードとしての配置・まとめ方は「ダッシュボードのカード構成・レイアウトの整理（Phase 21）」に従う（ログイン導線はVPNベンダーのカードへ、稼働状況は接続状態のカードへまとめる）。

## 設定ダイアログの入力項目

ユーザ向け設定の各項目を、以下のUI部品で編集可能にする。

| 設定項目 | UI部品 | 備考 |
|---|---|---|
| `killSwitch` | トグルスイッチ | ONでVPN切断検知時にLAN側通信を遮断する |
| `excludedDomains` | テキストボックスのリスト編集（追加・削除可能な複数行入力） | split-tunnelで除外する宛先ドメイン。1行1ドメインとして入力し、保存時に配列へ変換する |
| `transparentGatewayEnabled` | トグルスイッチ | 透過ゲートウェイモードの有効/無効 |
| `explicitProxyEnabled` | トグルスイッチ | 明示的SOCKS5/HTTPプロキシモードの有効/無効 |
| `explicitProxyAllowedCidrs` | テキストボックスのリスト編集（追加・削除可能な複数行入力） | 明示的プロキシモードで接続を許可するLAN側CIDR。1行1CIDRとして入力し、保存時に配列へ変換する |

`explicitProxyEnabled` がOFFの間は `explicitProxyAllowedCidrs` の入力欄を無効化（disabled）し、設定自体は保持したまま編集不可であることを視覚的に示す。

`defaultCountry`（デフォルト接続国）は廃止した（Phase 5）。接続処理に一度も使われていなかったうえ、「最後に接続した接続先」をシステムが記憶して既定選択とする方が利用者の意図に沿うため（下記「接続先リスト」参照）。

## 接続先リスト（Phase 5）

接続操作カードの接続先選択は、ドロップダウンに代えて、ping値に基づくグラフィカルなリストとする。

- **提示内容**: VPNベンダーCLIが返す接続先（国・都市）の一覧。1行が1接続先（都市単位。同一国に複数都市がある場合は別行）。各行に国コード、国名、都市名、ping値（ミリ秒）を表示する。ping値が取得できない接続先は「-」と表示し末尾に置く。
- **並び順**: ping値の小さい（速い）順。全タブ共通。
- **タブ**: 「すべて」（全接続先）と「お気に入り」（利用者がお気に入り登録した接続先のみ）を切り替えて表示できる。どちらのタブもping値の小さい順とし、「すべて」タブではお気に入りの接続先に★マークを表示する。
- **お気に入り**: 各行の★ボタンで登録・解除する。登録内容はAPIサーバに永続化し、再読み込み・別端末・別ブラウザでも共通とする（認証がなくLAN限定の運用のため、利用者全員で共有される）。お気に入りが0件のときは、その旨と登録方法を案内する。
- **絞り込み**: 国名・都市名・国コードのテキスト入力で、表示中のタブのリストを絞り込める（大文字小文字は区別しない）。並び順は変えない。
- **選択と既定選択**: 行をクリックして接続先を選択する（1つのみ）。未選択の間は、接続中なら現在の接続先、切断中なら最後に接続した接続先を選択済みとして扱い、リスト上で識別できるようにする。現在の接続先には「接続中」、最後に接続した接続先には「前回」のバッジを付ける。
- **接続ボタン**: 切断中に、選択済みの接続先（未選択なら最後に接続した接続先）へ接続する。選択済みの接続先が無い場合は操作不能とする。
- **「接続先を変更」ボタン**: 接続中に、現在の接続先と異なる接続先が選択されている間だけ、切断ボタンとは別に表示する。押下すると選択した接続先へ切り替える（切断ボタンは常に残す）。確認ダイアログは設けない。
- **再計測**: 「再計測」ボタンでリストを再取得し、ping値を更新する（ping値は取得時点の推定値であり、自動更新はしない。リスト表示中に並び順が勝手に変わるのを避けるため）。取得中はローディングを表示し、二重取得できないようにする。
- **取得失敗**: リストの取得に失敗した場合（未ログイン・プロキシ未応答等）は、リスト領域にエラー要約と「再取得」ボタンを表示し、接続操作は行えない（切断は可能）。
- **設定ダイアログとの関係**: 接続先の選択は設定ダイアログではなくこのリストに一本化する。

## 接続・切断ボタンの配置・強調（Phase 16）

- **配色**: ［切断］ボタンは、押しやすさと誤操作の見分けやすさのため、他の操作ボタン（primary等）と区別できる強調色（赤系）にする。［接続］ボタンは従来どおりprimary色のままでよい。
- **配置**: ［接続］［切断］ボタンは、接続操作カードの末尾（接続先リストの下）ではなく、画面上部のアカウント状態表示（ログイン導線・ログアウトボタンの近く）に置き、接続先リストの長さに関わらずスクロールせず押せる位置にする。ログイン・ログアウトの状態にかかわらず、VPNの接続状態に応じてどちらか一方を常に表示する（アカウント状態の判定に操作可否を左右させない。Kill Switch運用中は切断できることが重要なため）。
  - **【2026-09-22追記】** 当初は［切断］ボタンのみを移設したが、接続先リストが多数（数十件）になる構成では［接続］ボタンがリストの下に取り残され、同じ問題（スクロールしないと押せない）が残っていた。利用者からの指摘を受け、［接続］ボタンも同じ位置（アカウント状態表示の隣）へ移設し、接続状態に応じて［接続］［切断］のどちらか一方だけが表示されるようにした（`ConnectButton.tsx`・`DisconnectButton.tsx`。`webserver/design.md`参照）。

## ベンダーの選択（Phase 8）

管理者が有効化したVPNベンダーの中から、使うベンダーをWeb UIで選べる（`specs/requirements.md`「VPNベンダーの選択（Web UI）」）。

- **表示**: ダッシュボード上部に、有効なベンダーの選択部品（各ベンダーの表示名。選択中が分かる）を置く。有効なベンダーが1つだけのときは、選択肢を出さず、ベンダー名のみを表示する（従来の画面と同じ操作感）。
- **利用不可のベンダー**（ランナーが起動していない等）: 選択肢には残したまま無効化し、理由を表示する（他の制限表示と同じ流儀）。
- **切替**: 選択すると、接続中でなければ即座に切り替える。**接続中は確認ダイアログを出し**（現在のVPNを切断してから切り替えること、Kill Switch ONの間はLAN機器の通信が遮断されることを明示）、承諾されたときだけ切り替える。切替中はベンダー選択・接続操作・ログイン操作を無効化する。切替に失敗したら（切断失敗等）、選択は元のベンダーのままで、原因をトーストで通知する。
- **画面の追従**: 切替が成功したら、接続状態・ログイン状態・プラン・操作の実行可否・接続先リスト・お気に入り・「前回」の表示・選択中の接続先を、新しいベンダーのものへ入れ替える（前のベンダーの表示や選択を引き継がない）。接続状態の表示には選択中のベンダー名を含める。
- **共有**: 選択はサーバ側に保持されるため、別のブラウザ・端末で開いても同じベンダーが選択されている。ポーリングで他所からの切替にも追従する。

## 操作の制限表示（Phase 7）

プロバイダの機能差・プラン制限（未対応・未ログイン・プラン制限）に応じて、実行できない操作を制限する（`specs/requirements.md`「プロバイダごとの機能差・プラン制限への対応」）。制限の有無・理由はAPI（`GET /v1/connection/capabilities`）が返す値に従い、Webサーバは判定ロジックを持たない。

- **制限の見せ方**: 該当する操作の部品は**残したまま無効化し、理由文を表示する**（画面から消さない。有料版で使える機能の存在と、使えない理由が分かるようにするため）。理由文はAPIが返す`message`をそのまま表示し、無効化した部品からスクリーンリーダー等でも理由を辿れるようにする。
- **オペレーションと部品の対応**:

| オペレーション | 部品 | 制限時の表示 |
|---|---|---|
| `login` | ログイン導線 | 非対応のときは導線ごと出さず理由を表示（ログインできないプロバイダは想定しないが、規則としては同じ） |
| `logout` | ログアウトボタン | 無効化＋理由 |
| `locationList` | 接続先リスト（タブ・絞り込み・行） | リスト全体を出さず、理由文の枠を表示する（一覧を取得しない） |
| `locationFavorites` | ★ボタン | 無効化＋理由 |
| `pingMeasurement` | 「再計測」ボタン | 無効化＋理由 |
| `connectToLocation` | 選択した接続先への［接続］ | 無効化＋理由 |
| `connectAuto` | ［接続］（接続先を指定しない接続） | `connectToLocation`が使えないときに、［接続］として表示する（両方使えるときは表示しない。接続先を選んで接続する導線を優先する） |
| `changeLocation` | ［接続先を変更］ | 無効化＋理由（接続中に別の接続先を選んだときのみ表示される従来の条件は維持） |
| `disconnect` | ［切断］ | 無効化＋理由（通常は常に可） |

- **ログイン導線**: ログイン方式（`GET /v1/session`の`loginMethod`）に従い切り替える。`deviceUrl`は従来どおり［ログイン］ボタンで認証URLを表示する。`credentials`は、ユーザー名・パスワード・2段階認証コード（任意）の入力フォームを表示する。ログイン済みの間は、アカウントの状態（プラン名）と［ログアウト］を表示する。プラン名の直後に、補足情報（`GET /v1/session`の`plan.usageNote`。例: 今月分の残りデータ通信量）があれば併記する（Phase 13。無ければ何も表示しない）。
- **秘密情報の扱い**: パスワード・2段階認証コードは、送信の成否にかかわらず送信直後に画面の入力欄から消す。ブラウザへの保存（localStorage・自動入力の提案）や、トースト・画面への表示をしない。
- **状態の取得**: 操作の実行可否は、接続状態と同じ周期（画面表示中のみ）で取得する。取得に失敗した場合は制限をかけない（判定できないことを理由に操作を塞がない）。実行可否が初めて得られるまで（読み込み中）は、接続先リストの取得を開始しない（制限されるプロバイダで無駄な取得とエラー表示が出るのを避けるため）。
- **プラン制限による失敗**: `403`（`operation_restricted`）は、他の失敗と区別した文言（「現在のプランでは利用できない操作です」）でトースト通知し、直後に実行可否を再取得して画面へ反映する。

## プランで接続できる接続先の参考表示（Phase 12）

接続先リストが「プラン制限」で使えないとき（`locationList`が`planRestricted`）、理由文の枠に続けて、**そのプランで接続できる国の一覧を参考として表示する**（`specs/requirements.md`「プランで接続できる接続先の参考表示」）。

- 一覧は`GET /v1/connection/available-locations`の値に従う。空（取得できない・対象外）のときは何も表示しない。
- 表示は選択・操作できない部品にする（ボタン・リンクにしない）。「自動接続で、次のいずれかの国のサーバに接続されます（選択はできません）」等の、選べないことと自動接続であることが分かる説明を添える。国名（日本語）と、都市名を併記する。
- 接続先リストが使える（制限がない）プロバイダ・プランでは、取得も表示もしない。取得の失敗は画面に出さず（参考情報のため）、表示しないだけとする。

## 参考一覧での現在の接続先の表示（Phase 16）

「プランで接続できる接続先の参考表示」（Phase 12）の一覧は、`GET /v1/connection`が返す接続状態（CLIが報告する都市名）と突き合わせられるときは、現在接続中の国が参考一覧の中のどれかを示す。

- **見た目**: 参考一覧は、接続先リスト（Phase 5「接続先リスト」）と同じ行形式（国コード・国名・都市名の表示、バッジ）で表示し、一覧の性質（選択できない）を保ったままUIの見た目を統一する。
- **選択・お気に入り**: 行のクリックによる選択、★（お気に入り）は常に無効化する。参考一覧はUI表示としての共通化に留め、実際に選択・登録できるようにはしない。
- **現在の接続先の特定**: `GET /v1/connection`の`location`（CLIが報告した都市名）と、参考一覧の各国が持つ都市名（`cities`）を、大文字小文字を区別せず突き合わせる。一致する国が見つかれば、その行に「接続中」バッジを付け、主表示を報告された都市名にする（見つからない・未接続・都市名が無い場合は、従来どおり国名のみの表示のまま）。
- **ping値の表示**: 参考一覧は生存確認を伴わない静的なサーバ一覧に基づくため、通常はping値を持たない。列自体は、そのベンダーのCLIがping計測に対応しているか（`GET /v1/connection/capabilities`の`pingMeasurement`が、プラン制限ではなく非対応（`unsupported`）を理由に実行不可か）で出し分ける。対応していても値が無ければ「-」と表示する。

## 未実装機能の暫定表示（Phase 4〜Phase 14。明示的プロキシ分はPhase 6で除去済み）

`excludedDomains`（Phase 14）はWeb UIから設定値の編集・保存ができるが、対応するproxy側処理が実装されるまで実際には反映されない。利用者が「保存できた＝効いている」と誤解しないよう、該当する設定項目に「未対応（反映されません）」の旨を表示すること。対応フェーズ完了時に除去する。明示的プロキシはPhase 6で実装済みのため暫定表示の対象外とし、稼働状況欄に実際の稼働状況（稼働中・停止・未構成・起動失敗の繰り返し等）を表示する。

## ダッシュボードのカード構成・レイアウトの整理（Phase 21）

Phase 16までの配置改善（ログイン導線の隣への接続/切断ボタンの集約）は、その後カードの役割が増えるにつれて次の問題を生んだため、カードの役割を以下のように整理し直す。

- **ログイン導線の配置**: VPNベンダーへのログイン・ログアウトの導線（ログインフォーム／ログインボタン、ログイン済みのプラン表示、ログアウトボタン）は、接続先の選択・接続操作を行うカードではなく、**VPNベンダー選択のカードにまとめる**。ベンダーを選ぶ操作とそのベンダーへログインする操作は一体の関心事であり、UIの一貫性のため同じカードに置く（従来はSessionCardが接続操作カードに同居していた）。
- **稼働状況カードの統合**: 「稼働状況」（透過ゲートウェイ・明示的プロキシの実際の稼働状態）は、独立したカードとして表示せず、**接続状態の表示・接続/切断ボタンと同じカードにまとめる**。接続の状態（接続中/切断・接続国）と、その結果としての実際の稼働状況は、利用者にとって同じ「今どうなっているか」を確認する関心事であるため。
- **制限理由の重複表示の解消**: 未ログイン等により［接続］ボタンが無効化されるとき、その理由文（例:「ログインしてください」）を［接続］ボタンの近くと接続先リストの制限表示の、2箇所に重ねて表示しない。同じ理由文は、**接続先リスト側（画面のより下部）の制限表示にのみ**表示する。［接続］ボタンは無効化された理由を持つが、視覚的な理由文は表示せず、支援技術からはリスト側の理由文を参照できるようにする（`aria-describedby`）。
- **画面の縦幅**: ダッシュボードは、接続先リストの内部スクロール（`location-scroll`）を除き、ページ全体をスクロールしなくても1画面（ブラウザの表示領域の高さ）に収まるようにする。

これにより、ダッシュボードのカード構成は次のとおりになる。

| カード | 内容 |
|---|---|
| VPNベンダー | ベンダー選択（複数のとき）、ログイン導線・ログアウト・アカウント状態（プラン名等） |
| 接続状態 | 接続中/切断の表示、接続/切断ボタン、稼働状況（透過ゲートウェイ・明示的プロキシ） |
| 接続操作 | 接続先リスト、選択中の接続先、「接続先を変更」ボタン |

## モバイル表示・入力欄の視認性改善（Phase 22）

利用者からの指摘（スマートフォンでの操作時の意図しない拡大表示、入力欄の視認性）を受け、以下を要件とする。機能追加は行わず、既存の表示・操作の見た目のみを変更する。

- **フォーカス時の意図しない拡大の防止**: スマートフォン（iOS Safari等）でテキストボックスへフォーカスした際、ブラウザが自動的に画面を拡大表示する挙動を防止すること。
- **入力欄の視認性向上**: テキストボックス（ユーザー名・パスワード・2段階認証コード・接続先の絞り込み等、入力を受け付けるすべての欄）について、文字サイズを現状より拡大し、枠線の色をブラウザ・OSの既定色ではない、システム内で意図的に定めた色に変更し、内側の余白（padding）を設けて視認しやすくすること。
- **アカウントのログイン状態表示の簡素化**: 「アカウント: 未ログイン」の文言は表示しないこと（ログインフォーム自体が表示されていることでログインしていないことは自明であり、冗長なため）。ただし、ログイン状態は、接続状態の表示（接続中/切断）と同様に、色によって視覚的に判別できるようにすること。
- **接続先設定フォームの高さ**: 接続操作カード（接続先リストを含む）は、接続先リストまたは参考一覧に実際に表示する項目があるときにのみ、画面の残り高さいっぱいまで縦に広がるようにすること。表示する項目がないとき（取得中・0件・制限理由のみで参考一覧も無いとき等）は、内容に必要な高さのみを占め、余分な空白を確保しないこと。
- **フッターの追加**: 画面の末尾に小さなフッターを設け、本リポジトリのGitHub上のページへのリンクをGitHubのロゴとともに表示すること。フッターは他の主要な操作の妨げにならない、控えめな大きさ・配置とする。

## ベンダー選択のプルダウン化・PWA対応・モバイル表示の改善（Phase 23）

利用者からの指摘（VPNベンダー選択カードの画面のデッドスペース、入力欄の枠線色が他のUIと系統が異なる、スマートフォンでのスクロール、PWA未対応）を受け、以下を要件とする。機能追加（業務ロジック）は行わず、既存の表示・操作の見た目のみを変更する。

- **VPNベンダー選択のプルダウン化**: 有効なベンダーが複数あるときの選択部品を、ラジオボタンの並び（ベンダー数ぶんの行を必要とし、画面の空白が目立つ）からプルダウン（1行で収まる）へ変更する。選択できる値・切替時の確認（接続中の切替は確認ダイアログを出す）・利用不可ベンダーの無効化・理由表示は従来どおり維持する。
- **プルダウンとログイン/ログアウト導線の同じ行への配置**: プルダウンの隣（同じ行）に、そのベンダーへのログイン/ログアウトの単発ボタン（URL提示型のログインボタン、またはログアウトボタン）を配置し、画面のデッドスペースを減らす。資格情報入力型のログイン（ユーザー名・パスワード欄を持つフォーム）は、ボタン単体に切り出せないため、従来どおりプルダウンの下の行にフォームごと表示する。
- **プルダウンの装飾**: プルダウンはブラウザ・OS既定の見た目（system UI）を使わず、他のテキスト入力欄と揃った、テキストボックスのような装飾にする（枠線・padding・フォーカス時の強調を他の入力欄と統一する）。
- **入力欄の枠線色の一貫性**: 入力欄の枠線色（`--input-border`、Phase 22で導入）が紫（他のUIの配色系統と異なる）になっている点を、他のUI（枠線・アクセント色等）と系統が近いグレー系の色へ変更する。
- **スマートフォンでのスクロール防止**: スマートフォン等の狭い画面幅でも、Phase 21で満たした「ページ全体はスクロールしない（接続先リストの内部スクロールを除く）」を維持する。狭い画面幅では、カードの余白・行内配置を詰め、必要に応じて要素を縦に積み替えることで、内容のはみ出し・折り返しによる意図しないスクロールを防止する。
- **PWA対応**: ホーム画面への追加・スタンドアロン表示（ブラウザのアドレスバー等を持たない画面）ができるよう、Webアプリマニフェスト・アイコン・Service Workerを用意する。実際にインストール可能になる（Service Workerが有効化される）かどうかはブラウザのセキュアコンテキスト要件（HTTPSまたはlocalhost）に依存し、本要件はそのための資材・登録処理を用意することまでとし、配信のHTTPS化自体は本フェーズのスコープ外とする。

## ログインボタンもプルダウンの隣へ・入力欄の枠線色をボタン同等の薄さへ（Phase 24）

Phase 23実施後の利用者からの指摘（資格情報入力型ログインのフォームがプルダウンの隣ではなく下に大きく表示されたままであること、入力欄・プルダウンの枠線のグレーが濃すぎること）を受け、以下を要件とする。機能追加（業務ロジック）は行わず、既存の表示・操作の見た目のみを変更する。

- **ログインボタンもプルダウンの隣へ**: URL提示型ログインだけでなく、資格情報入力型ログイン（ユーザー名・パスワード欄を持つフォーム）についても、未ログイン時はプルダウンの隣（同じ行）に「ログイン」ボタンを表示する。フォーム（ユーザー名・パスワード等の入力欄）は、この「ログイン」ボタンを押すまで表示しない。ボタンを押した後は、プルダウンの下の行へフォームを表示する。
- **入力欄の枠線色をボタン同等の薄さへ**: Phase 22・23で定めた`--input-border`（入力欄・プルダウンの枠線色）が、通常のボタンの枠線色より濃いグレーになっている点を、ボタンの枠線色と同程度の薄さへ変更する。

# Web⇄API通信の要件

ブラウザは常にWebサーバの単一オリジンにのみアクセスし、Webサーバが `/api/*` パス配下のリクエストをAPIサーバへリバースプロキシする必要がある。これによりブラウザ視点でのCORS設定が不要になる。また、APIコンテナはホストポートを公開せず内部ネットワークのみに存在させることができ、LAN上の攻撃対象をWebサーバの1ポートに絞れる。

**【Phase 25】** Webサーバ・APIサーバを別ホストへ分離配置できるようにする際も、この同一オリジン構成は維持すること。リバースプロキシ先（APIサーバのオリジン）はホスト名・ポートを可変にでき、HTTPSで接続できること。セッションCookieによる認証（下記「利用者認証の要件」）を、ドメイン分離に起因する問題（Cookie共有不可等）を生じさせずに追加できること。

# 利用者認証の要件（Phase 25）

- 未認証の状態では、ダッシュボードを含むAPI操作を伴う画面を表示・操作できないこと。ログイン画面へ誘導すること。
- ログインは単一の共有パスワードの入力のみとする（利用者ごとのアカウント作成・切替は不要）。
- ログイン後はセッションCookieにより認証状態を維持し、ブラウザの再読み込み・別タブでも再ログインを求めないこと。
- APIサーバがセッション切れ・未認証（`401`）を返した場合、Web UIはログイン画面へ戻ること（実行中の操作は失敗として通知する）。
- ログアウト操作を提供すること。

# 状態管理の要件

- VPN接続状態、Kill Switch状態等を、画面表示中はAPIサーバから定期的に取得できること。接続先リスト（ping値を含む）は定期取得の対象とせず、画面表示時と利用者の再計測操作時にのみ取得する。
- 接続/切断等の操作リクエスト送信中はUI上で操作を二重送信不可にし、完了までローディング状態を表示すること。
- APIサーバからのエラーレスポンスは、ユーザに分かる形でトースト表示等に変換すること。生のエラーメッセージ（コマンドのstderr等）は詳細表示（折りたたみ）に留め、通常表示では要約のみとする。
