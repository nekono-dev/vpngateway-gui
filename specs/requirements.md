# システムの目的

AdguardVPN・Proton VPN・NordVPN等をLinuxサーバ上にインストールし、VPNゲートウェイとして構築する構成において、Linux上でCLI入力する手間を省くため、Webアプリケーションとして代用できるようにする。

# システム要件

OSは以下に対応する。

- Debian（RaspberryPiOS）
- Ubuntu（24.04 LTSなど）

# システムの互換性

このシステムはベンダロックインを防ぐため、各社CLIの操作内容をサーバ管理者が指定する。つまり、いくつかの実施可能な操作に対して、実行するコマンドを管理者自身が設定する。ex: VPNに接続するコマンド「adguardvpn-cli connection」
一部のコマンドについては、プレースホルダーに対応する。 ex: VPNの接続先を変更する「adguardvpn-cli connection -l %COUNTRY%」

これらの設定は、責務の異なる2種類の設定として明確に分離する必要がある。

- **管理者向け設定（VPNクライアント操作プロファイル）**: サーバ管理者が作成し、プロキシサーバ上で実行するVPNベンダーCLIのコマンド体系（プレースホルダー含む）を定義する。エンドユーザー（Web UI利用者）は変更できない。
- **ユーザ向け設定**: Web UI利用者がGUIから変更できる運用設定。例: VPNトンネルを経由させない宛先ドメインを指定する「VPN除外設定（split-tunnel）」、Kill Switch（後述）のON/OFF、お気に入りの接続先、プロキシモード（透過ゲートウェイ／明示的SOCKS5・HTTPプロキシ）の切替。APIサーバが受理し永続化する。

接続先（VPNサーバの所在地）は、VPNベンダーCLIが返す接続可能な一覧（国・都市・ping値）を都度取得して利用者に提示する。管理者向け設定に接続先の一覧を静的に持たない（ベンダー側のサーバ増減で陳腐化するため）。最後に接続した接続先は、システムが記憶して次回の既定選択に用いる（利用者が設定する項目ではない）。

「ホストの変更を最小限に抑える」とは、ホストを一切変更しないという意味ではなく、**ホスト側で変更するファイル数を最小限にする**という意味である。

# プロバイダごとの機能差・プラン制限への対応

VPNプロバイダ（AdGuard VPN・Proton VPN等）は、CLIのコマンド体系だけでなく、**提供する機能**（接続先の選択・ping値付き一覧・ログイン方式など）と、**契約プラン（無料/有料）による制限**が異なる。特定プロバイダの都合をWeb UI・APIの本体に埋め込まず、どのプロバイダを使った場合でも同じ仕組みで対応できること。

- システムは、Web UIの各操作について「その操作に対応するコマンドが実行可能か」を判定し、実行できない操作をWeb UI上で制限（無効化し、理由を表示）できなければならない。実行不可になる原因は次の3種で、利用者が区別できること。
  - **プロバイダ非対応**: そのプロバイダのCLIに該当コマンドが無い（例: Proton VPNにはping値付きの接続先一覧が無い）。
  - **プラン制限**: コマンドはあるが、契約プランでは実行できない（例: Proton VPN無料版は接続先を選べず、最速の無料サーバへの自動接続のみ）。
  - **未ログイン**: ログインしていないため実行できない。
- プラン制限の有無は、利用者が手で設定するものではなく、**プロバイダCLIの状況から自動判定**する（副作用のない読み取り専用コマンドの出力から判定する）。判定できない場合は制限せず、実行時にCLIが失敗すればエラーとして通知する（判定不能を理由に操作を塞がない）。
- 制限の定義（どのコマンドの出力がどのプランを表し、何が制限されるか）は管理者向け設定（VPNクライアント操作プロファイル）に外だしし、プロバイダ追加時にAPI・Web UI本体の改修を要求しない。
- ログイン方式もプロバイダで異なる（AdGuard VPN: ブラウザ認証用URLの提示、Proton VPN: ユーザー名・パスワード・2段階認証コードの入力）。管理者向け設定で方式を宣言し、Web UIはそれに従って導線を切り替える。パスワード等の秘密情報は、CLIの標準入力にのみ渡し、コマンド引数・ログ・エラー応答・画面のいずれにも残さない。
- Web UIの制限はあくまで利便のための表示であり、セキュリティ境界ではない。実行可否の最終判断はプロバイダCLIが行い、APIは実行結果（プラン制限による失敗を含む）を利用者へ返す。

# VPNベンダーの選択（Web UI）

Web UI利用者は、管理者が有効化したVPNベンダー（AdGuard VPN・Proton VPN等）の中から、**使うベンダーをWeb UIで選べる**こと（Phase 8）。

- 選べるのは、管理者が用意（`vendors/`のベンダーバンドル）し、有効化（`.env`）したベンダーのみ。利用者がコマンドを指定できる範囲は従来どおり管理者のプロファイルだけに限る（Web UIで選べるのは「どれを使うか」だけで、コマンド内容は変更できない）。
- **VPNへの接続は常に1ベンダーのみ**（切替式）。透過ゲートウェイ・Kill Switch・明示的プロキシはトンネル1本を前提とし、同時に複数のVPNへ接続することは対象外（要求されれば別課題）。選択中のベンダーが、接続・切断・ログイン・接続先一覧など全ての操作の対象になる。
- ベンダーごとに、ログイン状態・お気に入り・最後に接続した接続先・プラン（無料/有料）による制限を**独立に保持**する（ベンダーを切り替えても、元のベンダーのログインや設定は失われない）。
- 接続中にベンダーを切り替えたときは、確認のうえ、現在のVPNを自動で切断してから切り替える。Kill Switch ON の場合、切断から新ベンダーへの接続までの間、LAN機器の通信は遮断される（利用者に確認ダイアログで明示する）。
- 選択したベンダーは、サーバ側に保持する（ブラウザの再読み込み・別端末・別ブラウザでも共通）。
- ベンダーごとのCLI実行環境（例: Proton VPN CLIのNetworkManager等）は、ベンダー別のコンテナに閉じ、ベンダーの追加が他のベンダーの実行環境に影響しないこと。

# プランで接続できる接続先の参考表示（Phase 12）

契約プランによっては、接続先を利用者が選べない（例: Proton VPN無料版は、最速の無料サーバへの自動接続のみ）。この場合でも、利用者が「自動接続でどの国・都市のサーバに繋がりうるか」を知れること。

- 接続先を選べないプランのとき、Web UIは、そのプランで接続できる国（と都市）の一覧を**参考情報として**表示する。選択・接続の操作にはしない（接続先の指定は制限されたままで、接続は自動接続のみ）。
- この情報は、プロバイダCLIが自身のキャッシュとして既に持っているサーバ一覧から得る（追加のネットワーク通信・追加の認証情報を要求しない）。取得元と読み取り方は管理者向け設定（プロファイル）で宣言し、特定のプロバイダの形式をAPI・Web UI本体に埋め込まない。
- 情報が得られない場合（キャッシュが無い・読めない・プランが対象外）は何も表示しない。得られないことを理由に、接続などの操作を塞がず、エラーにもしない。
- 表示は最新のキャッシュに従う（CLIが更新する）。接続できることの保証ではない（サーバの負荷・障害・混雑により、自動接続は別の国に繋がりうる）。

# プラン制限のバリエーション：候補の絞り込みと補足情報の参考表示（Phase 13）

契約プランによる制限には、「プロバイダごとの機能差・プラン制限への対応」で扱う**操作自体を実行できない**もの（例: Proton VPN無料版は接続先を選ぶ操作自体ができない）だけでなく、**操作は実行できるが結果の候補が絞り込まれるだけ**のものがある（例: AdGuard VPN無料版は接続先を指定した接続・接続先一覧の取得のいずれも実行でき、一覧に含まれる接続先の数だけがプランに応じて絞り込まれる）。

- 後者の制限は、既存の「操作の実行可否（capability）」の仕組み（オペレーション単位でのunsupported/notLoggedIn/planRestricted判定）では表現しない。接続先一覧の取得コマンドが返す値をそのまま使えば表現できるため、無理に制限として扱わない。あるプロバイダ・プランで「選べる操作だが候補が少ない」ことは、そのコマンドの応答が少ないことそのもので表現され、追加の抽象化・分岐を要しない。
- 契約プランには、操作の実行可否とは別に、利用者向けの**補足情報**（例: 今月分の残りデータ通信量）が付随する場合がある。この情報が得られるとき、Web UIに参考として表示できること。取得元・読み取り方は管理者向け設定（プロファイル）の宣言で表し、特定プロバイダの文言・単位をAPI・Web UI本体に埋め込まない。
- 補足情報は接続の可否・速度に影響しない（表示するだけで、実際の速度低下等の挙動を検知・警告する機能ではない）。取得できない場合は表示しないだけとし、エラーにしない（プランで接続できる接続先の参考表示と同じfail-open方針）。

# ベンダー非依存性（Phase 10）

このシステムのWeb UI・API・ネットワークコンテナ・ランナーの実行部・共通インストーラは、**特定のVPNベンダーに依存しない**。ベンダー間の差は、管理者が用意する設定（プロファイル）と、ベンダーごとの実行環境（**ベンダーバンドル**）にのみ置く。

- **本番のソースコードにベンダー固有の値を含めない。** ベンダーのID・名称、CLIのコマンド名・出力書式・エラー文言、ベンダーによる分岐（ベンダー名を条件にした処理、ベンダー名を前提にした既定値・特例）を、実行コード・スクリプト・composeの共通部に書かない。コメントやエラーメッセージの例にも書かない（実例は仕様書とバンドルに書く。コメントに固有名を残すと、実装が変わったときに嘘になるため）。
- **ベンダー間の差が必要なときは、抽象化して設定（プロファイル）で表す。** コードの分岐は「プロファイルで宣言された機構」（例: ログイン方式）に対してのみ行い、ベンダーに対しては行わない。ベンダー固有になりうる項目に暗黙の既定値を置かない（プロファイルで明示させ、欠けていれば起動を失敗させる）。
- **ベンダーの追加・削除は、ベンダーバンドル（`vendors/<ベンダーID>/`）の追加・削除だけで完結する。** バンドルは、そのベンダーのプロファイル・ランナー（イメージ・composeのサービス・ボリューム）・ホスト側の追加手順（必要な場合のみ）を持つ。共通部（API・Web・ネットワークコンテナ・composeの本体・共通インストーラ）の改修を要求しない。
- 上記を機械的に検査できること。ベンダー固有の語を本番コードから検出する検査を、テストの一部として常に実行する。
- 例外として、仕様書・WBS・E2E・単体テスト・ベンダーバンドルの中には、ベンダー固有の情報を置いてよい。

# インストール（Phase 11）

- **クリーンなベアメタル（Debian系: Debian・Raspberry Pi OS・Ubuntu）で、1コマンドでプラットフォームを導入・起動できること**（`curl -fsSL <URL> | sudo sh`形式）。事前にDocker・git・リポジトリの取得・設定ファイルの作成を利用者に求めない。導入の範囲は、Docker（公式リポジトリ）と共通の依存パッケージ、ホストの最小限の設定（IPフォワーディング・起動時のKill Switchガード・LAN側インターフェース名の検出）、ソースの取得、web・api・proxyの起動とする。
- **どのベンダーを有効にするかを、インストーラの1つの引数（`--providers`。例 `--providers adguardvpn,protonvpn`）で指定できること。** 同じ操作の再実行で、有効なベンダーの追加・削除ができる。
- **Web UIを配信するホスト側のポート番号を、インストーラの引数（`--web-port`）で指定できること。既定は80とする。** 省略時の再実行では、`.env`の既存の設定値を維持する。
- **`--providers`を省略した場合は、その時点で`vendors/`にある全てのベンダー（all）を有効にすること。** 対話での選択は行わない（既定を「全ベンダー」に一本化し、指定が無い限り常に決定できるようにするため）。
- **再実行（アップデート）できること（冪等）。** 再実行は、更新（新しい版の取得と再起動）・ベンダーの変更・修復に使える。既存の設定（LAN側インターフェース名等）とベンダーのログイン情報（ボリューム）は保持する。`--providers`を省略した再実行では、有効なベンダーの選択も上記の「全ベンダー」の規則に従うため、新しく`vendors/`へ追加されたベンダーは、利用者が何もしなくても次回の再実行から自動的に有効化される。
- **ベンダー固有のホスト側の前提は、共通インストーラに含めない。** ベンダーのCLIがホスト（ベアメタル）へのアプリケーションの導入を要する場合は、そのベンダーのバンドルの`install-host.sh`に分離する。共通インストーラは、有効にしたベンダーの`install-host.sh`だけを呼ぶ。Dockerのように全ベンダー共通のものは共通側に置く。
- **アンインストールできること（Phase 18・Phase 20）。** インストーラの引数（`--uninstall`）で、このインストーラが導入・作成したもの（docker composeスタック、IPフォワーディングの設定、起動時のKill Switchガード、有効なベンダーのホスト側の後始末、ソースの取得先ディレクトリ自体）を後始末できる。ベンダーのログイン情報（Dockerボリューム）は既定では削除し、再導入時に維持したい場合のみ`--keep-data`を指定して保持する。**アンインストールは、頒布されたブートストラップ（インストールと同じ`curl | sh`形式）だけで完結できること。** ソースの取得先ディレクトリを事前に用意しておく必要はない。Docker本体・依存パッケージは、他の用途と共有されうるため対象外とし、手動での削除に委ねる。
- **頒布**: インストーラのスクリプト（ブートストラップ）は、CIが、ブランチまたはタグに紐付けて（取得するソースのコミットを固定して）生成し、GitHub Releaseなどで頒布する。ブートストラップは、ソースの取得（`git clone`）から本体インストーラの実行までを行う。
- ホストへの変更を最小限にし、作成・変更するものを文書化する（`specs/design.md`「インストーラと頒布」）。

# 起動時の接続状態の復元（Phase 16）

VPN接続中に、ホスト・APIコンテナが意図せず再起動された場合（クラッシュ・停電・アップデートに伴う予期しない再起動等）、再起動後にプロセス終了時点の接続状態へ自動的に戻すこと。具体的には、APIコンテナの起動時、直前に接続中だった接続先へ自動的に再接続する。直前が切断中だった場合は何もしない（意図せず接続を開始させない）。詳細は`specs/apiserver/requirements.md`「起動時の接続状態の復元」参照。

# デプロイメント構成の分離（Phase 25）

- システムを構成する3つの実行単位（**Webサーバ**・**APIサーバ**・**ゲートウェイ**＝プロキシサーバとランナー群）を、それぞれ独立したホストへ分離して配置できること。ゲートウェイ（プロキシサーバ・ランナー）は、透過ゲートウェイ機能が`network_mode: host`を要するため常に同一ホストに同居し、分離の単位としては常に1つにまとまる（`specs/design.md`「システムの構成」）。
- 1つのAPIサーバに対し、ゲートウェイは常に1組（1対1）とする。複数ゲートウェイの同時管理は対象外（将来課題）。
- 単一ホストへ全実行単位をまとめて配置する構成（従来どおり）を既定・最も簡単な導入経路として維持すること。分離は運用者の選択（インストーラの引数）による。
- 分離配置は、開発・デプロイの疎結合化と、ゲートウェイ機（VPNトラフィックの中継を担う実機）の負荷低減を目的とする。ゲートウェイ機には、`network_mode: host`が必須なプロキシサーバ・ランナーだけを配置できるようにする。

# 通信路の保護（Phase 25）

分離配置により、実行単位間の通信がホストをまたぎうる（LAN内に閉じない）ため、経路の暗号化と送受信者の認証を行う。

- **ブラウザ⇄Webサーバ**、**Webサーバ⇄APIサーバ**: HTTPS（TLS、片方向）で保護する。
- **APIサーバ⇄ゲートウェイ**: 相互TLS（mTLS）で保護する。この経路はVPNベンダーCLIの実行・ホストのネットワーク制御（nftables）という強い権限を行使できるため、サーバ・クライアント双方の証明書検証を必須とする（`specs/proxyserver/design.md`「ゲートウェイ制御チャネル」）。
- 証明書はいずれも自己署名とし、インストーラが導入時に生成・配布する（運用者が個別にPKIを構築する必要はない）。分離配置時は、インストーラが運用者から受け取った接続情報（SSHアクセス先等）を用いて、必要な証明書を自動的に配布する（`specs/design.md`「ロール別インストールと証明書ペアリング」）。外部認証局（Let's Encrypt等）との連携は対象外（将来課題）。

# 認証・認可（Phase 25で改訂）

- Web UI利用者は、単一の管理者アカウント（ユーザー名・パスワード）によるログインを経てダッシュボードを利用できること（複数利用者のアカウント管理は対象外）。
- **アカウントは、インストーラではなくWeb UIの初回アクセス時に利用者自身が設定すること。** 以後は、設定画面から自由にユーザー名・パスワードを変更できること（変更には現在のパスワードの入力を要する）。
- ログイン状態はセッションCookieで維持する。未認証の状態では、アカウント未作成の判定・初回設定・ログイン以外のAPI操作を一切受け付けないこと。
- パスワードはWeb UI・APIサーバのいずれのコードにも平文で保持しない（ハッシュ化して保存する）。
- 本項は、Phase 1〜24の前提「現時点ではWeb UI／APIサーバへの認証機構を設けない。LAN内限定での利用を前提とする」を置き換える。分離配置によりLAN外からの到達性が生じうるため、認証を必須の境界とする。
