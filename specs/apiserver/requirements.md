# SPEC-API: APIサーバ要件定義

サービス全体設計（../design.md）で定義されたAPIサーバの要件を示す。

# 責務の範囲

- Webサーバから送信された命令を受理する。
- 管理者向け設定（VPNクライアント操作プロファイル）とユーザ向け設定を読み込み・永続化する。
- 接続先（国・都市・ping値）の一覧を、VPNベンダーCLIから都度取得して提供すること。一覧の各要素には、お気に入り登録の有無と、最後に接続した接続先か否かを含める。管理者向け設定に接続先の静的な一覧は持たない（Phase 8で廃止）。
- 最後に接続した接続先と、利用者のお気に入り接続先を永続化すること。
- 現在の接続状態には、接続時に要求した国を含めること。VPNベンダーCLIの出力から国を取得できない場合でも、Web UIの再読み込みや別端末からの閲覧で接続国が失われないよう、APIサーバ側で保持すること（実際の接続先と乖離した国は返さない）。
- Web経由で受け取った値（接続先等）を、VPNクライアント操作プロファイルで定義されたプレースホルダーの許可パターンに対して検証し、実行コマンド（argv配列）を解決する。
- 解決したコマンドを、プロキシサーバの内部専用HTTPサーバへUDS経由で送信する。
- プロキシサーバからの実行結果を受け取り、Webサーバ向けに整形して返却する。
- 接続状態・操作履歴を保持し、Webサーバからの状態取得・監査ログ取得に応じる。
- **【Phase 11】** 有効なベンダーの一覧と、選択中のベンダーを保持・永続化し、Web UIからの切替を受け付けること。選択中のベンダー・ベンダー別の状態（ログイン状態・プラン・お気に入り・最後の接続先・接続先）は、ベンダーごとに独立に保持する（切り替えても元のベンダーの状態は失われない）。ベンダーの切替とその他のベンダー操作の競合を避けること。
- **【Phase 9】** 操作（オペレーション）ごとの実行可否（capability）を、プロファイルの定義・ログイン状態・契約プランから算出してWebサーバへ返すこと。実行不可の場合は原因（プロバイダ非対応／未ログイン／プラン制限）と、利用者向けの理由文を含める。ログイン状態・プランは、プロファイルで指定された副作用のない読み取り専用コマンドの出力から自動判定する。判定に失敗・不能な場合は制限しない。
- **【Phase 9】** ログイン方式（URL提示型／ユーザー名・パスワード入力型）をプロファイルの宣言に従って切り替えること。入力型では、パスワード・2段階認証コードをCLIの標準入力にのみ渡し、コマンド引数・監査ログ・エラー応答・APIのログのいずれにも残さないこと。ログアウトも提供する。
- **【Phase 9】** プラン制限を理由にCLIが失敗した場合は、通常の実行失敗（422）と区別して通知し、以後その操作を制限として扱うこと。
- VPNベンダーCLIへのログイン代行を受理する。ログインもVPNクライアント操作プロファイルで定義された操作（`login`等）の一つとして扱い、接続・切断・状態取得と同様の経路でプロキシサーバへコマンドを解決・送信し、実行結果（stdoutに含まれるログインURL等）をWebサーバ向けに整形して返却する。

APIサーバ自身はVPNクライアントを直接操作せず、ネットワーク設定（iptables/nftables操作等）も行わない。それらは全てプロキシサーバの責務である。ログイン代行についても、実際にCLIを実行するのはプロキシサーバであり、APIサーバは他の操作と同様にコマンド解決・仲介のみを行う。

# 管理者向け設定「VPNクライアント操作プロファイル」

サーバ管理者が用意し、APIコンテナに読み取り専用（`:ro`）でマウントする設定。ベンダーごとに、実行可能な操作とそのコマンド、プレースホルダーの検証ルールを定義する（具体的なファイル形式・スキーマは../design.md参照）。

- コマンドはシェル文字列として保持してはならない。値の代入段階でシェルメタ文字（`;` `|` `` ` `` `$()` 等）が入り込んでも解釈される余地をなくす必要がある。
- APIサーバはWeb UIから渡された値が、プロファイルで定義された許可条件（正規表現・列挙値等）を満たすかを**必ず**再検証しなければならない。Web UI側でドロップダウン選択に限定していても、フロントエンドを信用しない。
- ベンダー追加は、ベンダーバンドル（`vendors/<ベンダーID>/`。プロファイルとランナー。`../design.md`「ベンダー非依存の設計原則」）の追加のみで対応できること（APIサーバ本体の改修を要求しない）。
- **【Phase 12】ベンダー非依存**: APIサーバのコードは、ベンダーのID・名称・CLIの出力書式を持たず、ベンダーによる分岐をしない（`../requirements.md`「ベンダー非依存性」）。ベンダー固有になりうる項目（接続先の表の列名・接続状態の判定と書式・ログイン方式・ログインの標準入力の書式・接続時の指定名の加工）は、プロファイルで明示させ、暗黙の既定値を持たない。欠けていれば起動を失敗させる。有効なベンダーの既定値も持たない。

# ユーザ向け設定

Web UIから変更可能な運用設定。APIサーバが永続化し、プロキシサーバへの反映が必要なものはUDS経由で通知する。

- **killSwitch**: VPN切断検知時にLAN側通信を遮断するか否か（デフォルト: 遮断する）。
- **excludedDomains**: VPNトンネルを経由させない宛先ドメイン（split-tunnel除外リスト）。
- **transparentGatewayEnabled**: 透過ゲートウェイモードの有効/無効。
- **explicitProxyEnabled**: 明示的SOCKS5/HTTPプロキシモードの有効/無効。
- **explicitProxyAllowedCidrs**: 明示的プロキシモードで接続を許可するLAN側CIDR。

# 提供するAPIの要求

- Webサーバ向けに、接続状態の取得・接続/切断の制御、選択可能な接続先（ping値付き）の一覧取得、お気に入り接続先の登録・解除、ユーザ向け設定の取得・更新、監査ログ取得、VPNベンダーCLIへのログイン代行の機能を提供すること。
- **【Phase 11で変更】** ベンダー（VPNクライアント操作プロファイル）は、管理者が有効化した複数のものからWeb UI利用者が1つを選べること。APIは、有効なベンダーの一覧の提供と、使うベンダーの切替（接続中は現在のVPNを切断してから切り替える）を提供する。既存の操作（接続・切断・ログイン・接続先一覧等）は全て、選択中のベンダーを対象とする。ベンダーロックインを防ぐ手段（実行コマンドを管理者向け設定として外だしする）は変えず、利用者が選べるのは管理者が有効化したベンダーの識別子のみである（コマンド内容は指定できない）。
- **【Phase 9】** ログイン状態の取得・ログイン・ログアウト（`/v1/session`）と、操作ごとの実行可否の取得（`/v1/connection/capabilities`）を提供すること。接続は、接続先を指定する場合としない場合（プロバイダによっては前者が使えない）の両方を受け付けること。
- APIはOpenAPI仕様として公開され、Web側のクライアント生成（コーディングルールは../design.md参照）の唯一の情報源となること。

# プロキシサーバとの内部通信に関する制約

- APIサーバからプロキシサーバへの命令送信は、コンテナ外部（LAN含む）から一切到達不能な経路で行うこと。
- 上記経路はテキスト化された解決済みコマンドをそのまま実行させるための内部チャネルであり、正式なAPI（OpenAPI公開対象）ではない。

# 入力検証・セキュリティ方針

- Web UIからのプレースホルダー値は、VPNクライアント操作プロファイルで定義された許可条件に対してAPIサーバが必ず再検証する。
- VPNクライアント操作プロファイルの設定は読み取り専用マウントとし、実行時にAPIサーバから改変されない。
- ユーザ向け設定（`excludedDomains` のドメイン形式等）についても、APIサーバ側で形式検証を行う。
- すべてのコマンド実行要求とその結果（exitコード、stdout/stderr要約）を構造化ログとして記録する。現時点で認証機構がないため、事後追跡性の確保が重要になる。

# エラーハンドリング方針

Webサーバに対し、エラーの原因を区別して通知できること。少なくとも以下を区別する。

- プレースホルダー検証失敗、未知のベンダー指定等の入力エラー。
- プロキシサーバへの接続失敗（UDS未応答等）。
- プロキシサーバ側でのコマンド実行失敗（非ゼロexit）。実行結果（exitコード・stderr要約）を通知内容に含めること。
- タイムアウト。
- **【Phase 9】** プラン制限（`403`）、およびプロファイルが対応していない操作（`501`）。
- **【Phase 11】** ベンダー切替中の競合（`409`）、切替時の切断失敗（`422`）、切替先のランナー利用不可（`502`）。
