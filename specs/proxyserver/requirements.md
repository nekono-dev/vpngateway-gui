# Phase 1における縮小構成（履歴）

Phase 1では`network_mode: host`・`cap_add:[NET_ADMIN]`・`/dev/net/tun`は付与せず、透過ゲートウェイ・明示的プロキシ・Kill Switchの実処理・インストールスクリプトは実装しなかった。実VPNベンダーCLIの代わりにモックCLIスクリプトを使用した。詳細はproxyserver/design.md「Phase 1における縮小構成」を参照。

# コンテナ構成（Phase 8で変更）

従来の「ベンダーごとに別のproxyコンテナ」を、責務ごとに次の2種類へ分ける（`specs/design.md`「ベンダーの選択と実行基盤」）。Web UIから使うベンダーを選べるようにするため、複数ベンダーのCLIへ同時に到達でき、かつネットワーク制御（nftables・3proxy）の所有者が1つに保たれる必要がある。

- **ネットワークコンテナ（`proxy`）**: 透過ゲートウェイ・Kill Switch・明示的プロキシ・トンネル検出・接続監視・設定の反映。ベンダーCLIは実行しない。
- **ランナーコンテナ（`runner-<ベンダー>`）**: そのベンダーのCLIの実行環境と実行要求の受け口。ネットワーク制御はしない。ベンダーごとに1つ。有効化されたベンダーの分だけ起動する（`../runner/`）。

ベンダーCLIの実行・状態監視・内部コマンド実行要求の受理はランナーの責務であり、**別のアプリケーションとして`../runner/`（要件・設計・タスク）に切り出した**。本ファイルはネットワークコンテナ（両モード・Kill Switch・接続監視）を扱う。ネットワークコンテナは、ベンダーCLI独自のKill Switch・経路制御とは競合せず（ランナー側でベンダーのKill Switchは使わない。`../runner/requirements.md`）、本システムのnftablesが唯一の遮断機構となる。

# 責務の範囲

- （ベンダーCLIの実行・状態監視は、Phase 8でランナーコンテナへ移動した。`../runner/requirements.md`）
- 透過ゲートウェイモードの提供（LAN機器がこのホストをデフォルトゲートウェイとした場合の、VPNトンネル経由でのNAT/フォワーディング）。
- 明示的SOCKS5/HTTPプロキシモードの提供。
- Kill Switchの実施（VPN切断検知時のLAN側通信の遮断／通過制御）。
- APIサーバからの設定反映・状態取得・接続状態の再確認要求の受理（内部HTTP。`POST /settings`・`GET /status`・`POST /connection-checks`）。

- **【Phase 8】** ネットワークコンテナは、ベンダーの種類に依存せずトンネルを検出し、APIからの通知（接続・切断・切替の直後）で接続状態を即時に再確認できること。
- **【Phase 10】** ネットワークコンテナのコード・イメージは、ベンダーのID・名称・CLIの書式を持たない（`../requirements.md`「ベンダー非依存性」）。ベンダー別のファイル（ランナーのDockerfile・エントリポイント・付属の設定）は、`proxy/`ではなくベンダーバンドル（`vendors/<ベンダーID>/`）に置く。
- **【Phase 25】** ネットワークコンテナは、APIサーバとゲートウェイ（プロキシサーバ・ランナー）を別ホストへ分離できるようにするため、APIサーバからの制御チャネルの単一の受信口（mTLS TCP）を兼ね、自分宛のリクエストの処理に加え、ランナー宛のリクエストを対応するランナーのUDSへ転送すること。相互TLSでAPIサーバを認証し、証明書が無効な接続は確立しないこと。ランナー自身は、この受信口を経由せず外部（ゲートウェイホスト外）から直接到達できてはならない。

# 対応必須のモード

以下2つのモードに両対応すること。

- **透過ゲートウェイモード**: LAN機器がこのホストをデフォルトゲートウェイとして設定した場合に、そのフォワード通信をVPNトンネル経由でNAT/MASQUERADEし、ゲートウェイを介した通信がVPNトンネル越しになるようにする。
- **明示的プロキシモード**: ホストがSOCKS5/HTTPプロキシサーバとして利用できるようなポート解放を行い、クライアントが個別にプロキシ設定することでVPNトンネル越しに通信できるようにする。

# Kill Switch

VPNトンネルが切断された場合の挙動は、ユーザ向け設定「**Kill Switch**」で制御する必要がある。

- ONの場合はLAN機器の通信を遮断し（フェイルクローズ）、VPN非経由での通信を防ぐ。
- OFFの場合は直接インターネットに抜ける（フェイルオープン）。
- デフォルトはONを推奨する。

# 権限に関する制約

必要以上の権限を与えないこと。`privileged: true` は使用しない。個別の権限（後述）で不足する場合のみ、実装時のPoCで追加を個別検討する。

# ドメイン迂回とDNS中継（Phase 14）

全体要求は`../requirements.md`「ドメイン単位の迂回（split-tunnel）とDNS中継」。プロキシサーバが担う技術的な要求は次のとおり。

- `excludedDomains`に一致するドメインの名前解決結果IP宛の通信を、透過ゲートウェイ・明示的プロキシのいずれでも、VPNを経由させず実回線から送出すること。IPの期限（DNSのTTL）が切れた後は迂回の対象から外れ、名前解決のたびに更新されること。
- LANクライアントの名前解決を中継するリゾルバを持ち、上流の自宅DNSサーバへ、クライアントを識別できる形で転送すること。
- 上流障害時の挙動（フェイルクローズ／公開DNSへのフォールバック）を設定どおりに実行すること。
- 手動DNS指定のクライアントを含めて中継する「53番リダイレクト」を、設定で有効化できること（既定は無効）。宛先が指定のCIDRに含まれる問い合わせは対象外にできること。
- 中継リゾルバの停止・障害が、Kill Switch・透過ゲートウェイの転送・明示的プロキシの本来の動作（名前解決以外）に影響しないこと。
- 問い合わせ内容（ドメイン名・クライアント）はゲートウェイのログへ記録しないこと（履歴は自宅DNSサーバの役割）。
